Huddle DMZ Portal

Beveiligde gateway tussen devcontainers en het internet — Firewall, Docker Proxy & Administratie

Wat Is Huddle?

Huddle is een veiligheidsproxy die fungeert als DMZ (Demilitarized Zone) tussen uw devcontainers en het externe netwerk. Het biedt een geconsolideerde laag voor netwerkbeveiliging, proxying en containerbeheer—speciaal ontworpen voor JetBrains DevContainers die via de IntelliJ IDEA / Rider IDE werken.

Huddle beschermt uw开发omgevingen door verkeer te filteren, Docker-toegang te beheren en gedetailleerde audit Logs bij te houden—terwijl het de devcontainer-erfvaring volledig behoudt.

Hoogtepunten van Huddle

  • Firewall Proxy — HTTP/HTTPS verkeer wordt automatisch omgeleid door Huddle, waar regels op per-container en globaal worden toegepast
  • Time-Limited Docker Access — Docker socket-toegang is tijdelijk en moet expliciet worden goedgekeurd via de UI
  • Per-Container Proxy Sockets — Elke container heeft een eigen Docker socket proxy met toegangscontrole
  • Management UI — Gebruiksvriendelijke webinterface voor het beheren van containers, firewallregels en Docker-toegang
  • JetBrains Integration — Volledige automatische configuratie voor IntelliJ IDEA en Rider remote development
  • SQLite Database — Persistente opslag van firewallregels, Docker-toegangsvergunningen en audit Logs

Architectuur

Huddle functioneert als de only exit point voor devcontainers. Elk container verkeer (HTTP/HTTPS) en Docker API calls moeten Huddle passeren. Dit maakt het mogelijk om:

🌐 Externe Wereld
Internet services, APIs, repositories
➤
🐧 Huddle Gateway
HTTP Proxy (80) + Management API (3000) + Firewall Engine
➤
🐳 Devcontainer
IntelliJ IDEA / Rider — proxy via huddle:80
➤
💻 JetBrains IDE
Lcl host — beheer via UI

Dataflow:

  1. Devcontainer maakt HTTP/HTTPS request → proxy via huddle:80 (geset via http_proxy env var)
  2. Huddle proxy ontvanger request, controleert firewall regel voor deze domain + container_id
  3. Als allow → forward naar doel; als deny → 403 Forbidden; als requested → 403 + create rule
  4. Als container Docker socket nodig heeft → bind-mount naar /tmp/dc-sockets/[container].sock
  5. Socket proxy controleert Docker grant in SQLite—tijdgebonden (1-120 minuten)
  6. Management UI (port 3000) helpt beheren: containers, rules, grants—alleen bestemde voor host

Componenten

🌐 HTTP Proxy (port 80)

Intercepteert alle HTTP/HTTPS verkeer van devcontainers, draait regels op via Rules Engine. Ondersteunt CONNECT voor HTTPS.

📦 Docker Socket Proxy

Per-container UNIX socket proxy met time-limited toegang. Elke container heeft eigen socket in /tmp/dc-sockets/.

🔧 Management API (port 3000)

REST API voor container management, snapshot images, firewall rules en Docker access grants.

🎨 UI Dashboard

React-achtige frontend met dark/light mode, container overzicht, firewall rules, audit logs en Docker access control.

Firewall Model

Huddle gebruikt een two-level policy system:

  • Per-Container Rules — Regels zijn gekoppeld aan specifieke container_id (com.intellij.devcontainer.id)
  • Global Rules — Regels met container_id IS NULL gelden voor alle containers

Policy check order:

  1. Is er een per-container rule voor deze domain? → Check status
  2. Is er een global rule voor deze domain? → Check status
  3. Als geen rule gevonden → creëer "requested" rule en geef 403

Status types:

  • requested — Nieuwe request, nog niet goedgekeurd
  • allow — Domain is toegestaan voor deze container
  • deny — Domain is geblokkeerd voor deze container

Docker Access Grants

Devcontainers kunnen alleen Docker API calling als ze een time-limited grant hebben. Grants zijn in de SQLite database met docker_grants table:

CREATE TABLE docker_grants ( container_id TEXT PRIMARY KEY, until INTEGER NOT NULL );

Grant levenscyclus:

  1. Container probeert Docker socket connectie
  2. Socket proxy ophaalt grant met getGrant(containerName)
  3. Als until > now() → allow; else → 403 Forbidden
  4. Grant verlengbaar via UI (max 120 minuten)

Container Start Workflow

Als u een devcontainer start via de UI:

POST /api/docker/start { "imageName": "base-devimage", "workspaceDir": "C:/projects/my-project", "containerName": "dc-my-project", "ideName": "intellij" }

Huddle voert deze stappen uit:

  1. Check of devcontainer-net network bestaat
  2. Maak per-container socket proxy via createContainerProxy(containerName, SOCKET_DIR)
  3. Build Docker container met:
    • Env vars voor http_proxy/https_proxy naar huddle:80
    • Mount volume JetBrains Remote Dev dist
    • Bind-mount workspace naar container
    • Bind-mount Docker socket proxy naar /var/run/docker.sock
    • Mounts NET_ADMIN capability
  4. Start container
  5. Run jb-config.sh via exec met User: 'root'

jb-config.sh — Container Setup Script

Elke container krijgt dit script uitgevoerd bij start (via docker exec root):

#!/bin/sh # Locate JetBrains Remote Dev directory & build number IDEA_DIR=$(ls /.jbdevcontainer/JetBrains/RemoteDev/dist/ | grep -i "idea" | sort -t- -k2 -V | tail -1) IDEA_PATH="/.jbdevcontainer/JetBrains/RemoteDev/dist/$IDEA_DIR" BUILD=$(grep -o '"buildNumber":"[^"]*"' "$IDEA_PATH/product-info.json" | cut -d'"' -f4) CODE=$(grep -o '"productCode":"[^"]*"' "$IDEA_PATH/product-info.json" | cut -d'"' -f4) # Write host-config.json voor JetBrains remote development printf '{"connectionParams":{"type":"docker","projectPath":"%s","deploy":"false","idePath":"%s","buildNumber":"%s","productCode":"%s"},"forwardPorts":{},"customizations":{"jetbrains":{}}}' "$PROJ" "$IDEA_PATH" "$BUILD" "$CODE" > /.jbdevcontainer/config/JetBrains/host-config.json # Configure curl to send X-Container-ID header (voor policy audit) CURL_LINE='--proxy-header "X-Container-ID: ${containerName}"' grep -qF "$CURL_LINE" /home/vscode/.curlrc 2>/dev/null || echo "$CURL_LINE" >> /home/vscode/.curlrc # Configure iptables DNAT for HTTP egress via Huddle HUDDLE_IP=$(getent hosts huddle | awk '{print $1}' iptables -t nat -C OUTPUT -p tcp --dport 80 ! -d "$HUDDLE_IP" -j DNAT --to-destination "$HUDDLE_IP:80" 2>/dev/null || \ iptables -t nat -A OUTPUT -p tcp --dport 80 ! -d "$HUDDLE_IP" -j DNAT --to-destination "$HUDDLE_IP:80"

Wat dit script doet:

  • Leest JetBrains Remote Dev build info → schrijft host-config.json
  • Voegt X-Container-ID proxy-header toe aan .curlrc (voor policy logging)
  • Configureert iptables DNAT: alle HTTP traffic (port 80) wordt omgeleid naar huddle:80
  • Container moet NET_ADMIN capability hebben (kan firewall regels wijzigen!)

Beveiligingsoverwegingen

Huddle is ontworpen als high-trust gateway met toegang tot de host Docker socket. De huidige implementatie heeft enkele bekende kwetsbaarheden die worden vermeld in de SECURITY.md bestand:

CRIT-01 Docker socket grant bypass via X-Container-ID header injection

CRIT-02 Container identity spoofing via client-controlled IP/cached headers

CRIT-03 Geen authenticatie op management API (port 3000) — bereikbaar van alle containers

HIGH-02 Unvalidated container/image/workspace inputs in Docker API & shell scripts

HIGH-03 Egress firewall ingewikkeld in container (met NET_ADMIN) → container kan iptables bypassen

Aanbevolen remediatie:

  • Bind management API naar 127.0.0.1 of UNIX socket (niet op devcontainer-net)
  • Vereis bear token of mTLS op alle /api/* routes
  • Verwijder NET_ADMIN capability of verplaats iptables filtering naar host bridge
  • Validate container/image/workspace inputs strikt met regex/allow-list

Opslaan & Backups

Huddle gebruikt SQLite database met WAL mode voor persistentie. Het bestand:

const DB_PATH = process.env.DB_PATH || '/data/huddle.db'

Back-up strategie:

  • Draai regelmatig sqlite3 huddle.db VACUUM voor compactie
  • Kopieer het DB bestand en archiveer naar off-site opslag
  • Test restore procedure periodiek

Debug & Logging

Huddle logt naar stdout/stderr. Belangrijke log messages:

  • [proxy] listening on :80 — HTTP proxy gestart
  • [api] listening on http://0.0.0.0:3000 — Management API gestart
  • [socket-proxy] container-name → /tmp/dc-sockets/container-name.sock — Socket proxy aangemaakt
  • [socket-proxy] DENY container-name: no active grant — Docker access geweigerd

Veilige log practices:

  • Geen password/secret logging
  • Geen request bodies in logs
  • Redact API response in DEBUG mode only

Veiligheid
