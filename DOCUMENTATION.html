Huddle DMZ Portal

Beveiligde gateway tussen devcontainers en het internet — Firewall, Docker Proxy & Administratie

Wat Is Huddle?

Huddle is een veiligheidsproxy die fungeert als DMZ (Demilitarized Zone) tussen uw devcontainers en het externe netwerk. Het biedt een geconsolideerde laag voor netwerkbeveiliging, proxying en containerbeheer—speciaal ontworpen voor JetBrains DevContainers die via de IntelliJ IDEA / Rider IDE werken.

Huddle beschermt uw ontwikkelomgevingen door verkeer te filteren, Docker-toegang te beheren en gedetailleerde audit logs bij te houden—terwijl het de devcontainer-ervaring volledig behoudt.

Snel starten

huddle.ps1 in de repo-root is het centrale startpunt. Het start een interactief PowerShell-menu waarmee je de gateway bouwt, herstart en snapshots beheert.

# In de repo-root .\huddle.ps1

Het menu biedt:

  • 1 — Snapshot maken van draaiende container
  • 2 — Devcontainer starten van snapshot (gebruikt Start-Snapshot.ps1)
  • 3 — Base image bouwen (base-devimage/)
  • 4 — Huddle bouwen en herstarten (gateway/)
  • 0 — Afsluiten

Na een Huddle-start is de Web UI bereikbaar op http://localhost:3000.

Hoogtepunten van Huddle

  • Firewall Proxy — HTTP/HTTPS verkeer wordt automatisch omgeleid door Huddle, waar regels per container en globaal worden toegepast
  • Time-Limited Docker Access — Docker socket-toegang is tijdelijk en moet expliciet worden goedgekeurd via de UI
  • Per-Container Proxy Sockets — Elke container heeft een eigen Docker socket proxy met toegangscontrole en label-isolatie
  • HostConfig validatie — Sandbox-escape vectoren (Privileged, CapAdd, host-binds, etc.) worden geweigerd bij container-spawn
  • Management UI — Angular 21 webinterface voor containers, firewallregels, Docker-grants en audit logs
  • JetBrains Integration — Volledige automatische configuratie voor IntelliJ IDEA en Rider remote development
  • SQLite Database — Persistente opslag van firewallregels, Docker-toegangsgrants en audit logs
  • Bugtracker — Ingebouwde bug-rapportage opslag (bugtracker/bugs, bugtracker/solved)

Architectuur

Huddle functioneert als de only exit point voor devcontainers. Elk container verkeer (HTTP/HTTPS) en Docker API calls moeten Huddle passeren. Dit maakt het mogelijk om:

Devcontainer (DMZ) Huddle Gateway Internet (allowlist) Host & operator

Dataflow:

  1. Devcontainer maakt HTTP/HTTPS request → proxy via huddle:80 (afgedwongen via iptables DNAT + http_proxy env var)
  2. Huddle proxy ontvangt request, controleert firewall-regel voor dit domein + container_id
  3. Als allow → forward naar doel; als deny → 403 Forbidden; als requested → 403 + create rule
  4. Als container Docker socket nodig heeft → bind-mount naar /tmp/dc-sockets/[container].sock
  5. Socket proxy controleert Docker grant in SQLite—tijdgebonden (1-120 minuten)
  6. Management API (poort 3000) is alleen bereikbaar vanaf de host — een source-IP gate weert alle requests vanaf devcontainer-net en dc-net-*

Componenten

🌐 HTTP Proxy (port 80)

Intercepteert alle HTTP/HTTPS verkeer van devcontainers, draait regels op via Rules Engine. Ondersteunt CONNECT voor HTTPS.

📦 Docker Socket Proxy

Per-container UNIX socket proxy met time-limited toegang. Elke container heeft eigen socket in /tmp/dc-sockets/.

🔧 Management API (port 3000)

REST API voor container management, snapshot images, firewall rules en Docker access grants.

🎨 UI Dashboard

Angular 21 frontend (in gateway/frontend/) met dark/light mode, container overzicht, firewall rules, audit logs, Docker access control en bugtracker.

Firewall Model

Huddle gebruikt een two-level policy system:

  • Per-Container Rules — Regels zijn gekoppeld aan specifieke container_id (com.intellij.devcontainer.id)
  • Global Rules — Regels met container_id IS NULL gelden voor alle containers

Policy check order:

  1. Is er een per-container rule voor deze domain? → Check status
  2. Is er een global rule voor deze domain? → Check status
  3. Als geen rule gevonden → creëer "requested" rule en geef 403

Status types:

  • requested — Nieuwe request, nog niet goedgekeurd
  • allow — Domain is toegestaan voor deze container
  • deny — Domain is geblokkeerd voor deze container

Docker Access Grants

Devcontainers kunnen alleen Docker API calling als ze een time-limited grant hebben. Grants zijn in de SQLite database met docker_grants table:

CREATE TABLE docker_grants ( container_id TEXT PRIMARY KEY, until INTEGER NOT NULL );

Grant levenscyclus:

  1. Container probeert Docker socket connectie
  2. Socket proxy ophaalt grant met getGrant(containerName)
  3. Als until > now() → allow; else → 403 Forbidden
  4. Grant verlengbaar via UI (max 120 minuten)

Container Start Workflow

Als u een devcontainer start via de UI:

POST /api/docker/start { "imageName": "base-devimage", "workspaceDir": "C:/projects/my-project", "containerWorkspace": "/workspaces/my-project", "containerName": "dc-my-project", "presentableName": "my-project", "ideName": "intellij", "empty": false }

Huddle voert deze stappen uit:

  1. Check of devcontainer-net en een eigen dc-net-<name> network bestaan
  2. Maak per-container socket proxy via createContainerProxy(containerName, SOCKET_DIR)
  3. Start Docker container met:
    • Env vars voor http_proxy/https_proxy naar huddle:80
    • Volume voor JetBrains Remote Dev dist
    • Bind-mount workspace naar container (alleen als empty=false)
    • Bind-mount per-container socket proxy naar /var/run/docker.sock
    • NET_ADMIN capability voor iptables DNAT
    • Label huddle.parent=<containerName> voor isolatie
  4. Start container
  5. Voer het container init-script uit via docker exec als root

Container init script

Bij elke container-start voert docker.ts een inline shell-script uit (geen los jb-config.sh bestand meer — alle logica leeft in gateway/src/docker.ts). Het script:

#!/bin/sh # Locate JetBrains Remote Dev directory & build number IDEA_DIR=$(ls /.jbdevcontainer/JetBrains/RemoteDev/dist/ | grep -i "idea" | sort -t- -k2 -V | tail -1) IDEA_PATH="/.jbdevcontainer/JetBrains/RemoteDev/dist/$IDEA_DIR" BUILD=$(grep -o '"buildNumber":"[^"]*"' "$IDEA_PATH/product-info.json" | cut -d'"' -f4) CODE=$(grep -o '"productCode":"[^"]*"' "$IDEA_PATH/product-info.json" | cut -d'"' -f4) # Write host-config.json voor JetBrains remote development printf '{"connectionParams":{"type":"docker", ... }}' > /.jbdevcontainer/config/JetBrains/host-config.json # Configure iptables DNAT for HTTP egress via Huddle HUDDLE_IP=$(getent hosts huddle 2>/dev/null | awk '{print $1}') iptables -t nat -A OUTPUT -p tcp --dport 80 ! -d "$HUDDLE_IP" \ -j DNAT --to-destination "$HUDDLE_IP:80"

Wat dit doet:

  • Leest JetBrains Remote Dev build info → schrijft host-config.json
  • Configureert iptables DNAT: alle HTTP traffic (poort 80) wordt omgeleid naar huddle:80
  • Na een Huddle-restart worden de DNAT-regels automatisch geactualiseerd met het nieuwe Huddle IP
  • Container heeft NET_ADMIN capability — vereist voor iptables, maar betekent dat container-interne firewall niet als security boundary kan dienen (egress wordt afgedwongen door het netwerk, niet door iptables in de container)

Beveiligingsoverwegingen

Huddle is ontworpen als high-trust gateway met toegang tot de host Docker socket. De security review uit SECURITY.md identificeerde meerdere critical/high-severity issues; de belangrijkste daarvan zijn inmiddels geadresseerd. Verificatie van de fixes loopt via SECURITY.md (Part B).

Geadresseerd (gefixt + verifieerbaar):

  • CRIT-03 Management API source-IP gate weert alle requests vanaf devcontainer-net en dc-net-* — alleen host kan de API bereiken (geverifieerd in T4)
  • CRIT-01/02 Per-container socket proxy + label-isolatie via huddle.parent; identity spoofing via X-Container-ID wordt geweigerd (T6)
  • HIGH-02 validateHostConfig() in socket-proxy.ts blokkeert Privileged, PidMode/IpcMode/UTSMode/CgroupnsMode/UsernsMode=host, CgroupParent, non-empty CapAdd/Devices/Sysctls, gevaarlijke SecurityOpt, host-path Binds en bind-type Mounts (T11)
  • HIGH-01 Pad-traversal op de static asset route is dichtgetimmerd

Inherent ontwerprestriciës (geen "bug" maar wel goed te weten):

  • Container krijgt NET_ADMIN voor iptables DNAT — egress filtering wordt daarom niet in de container afgedwongen maar door netwerk-routing naar Huddle
  • Huddle heeft de host Docker socket gemount; compromise van Huddle = root-equivalent op de host
  • Transitieve npm-dependencies kunnen alsnog CVE's bevatten; periodiek npm audit blijft nodig

Volledige historische analyse en het verificatieplan zijn samengevoegd in SECURITY.md.

Visie & Toekomst

🛡️ Geautomatiseerde Firewall

Machine learning-driven anomaly detection in HTTP traffic patterns; auto-block on suspicious behavior with 24h review period.

🕵️ uitgebreide Audit Logging

Sla alle proxy requests, Docker socket calls, en container lifecycle events op in een tamper-proof logboek met 90-dag retention.

📈 Security Score Metrics

Per-container security posture metrics: firewall compliance, grant usage, request patterns—visualiseer via dashboard KPIs.

Implementeer mTLS between containers and Huddle; replace X-Container-ID header with client certificate subject validation.

Opslaan & Backups

Huddle gebruikt SQLite database met WAL mode voor persistentie. Het bestand:

const DB_PATH = process.env.DB_PATH || '/data/huddle.db'

Back-up strategie:

  • Draai regelmatig sqlite3 huddle.db VACUUM voor compactie
  • Kopieer het DB bestand en archiveer naar off-site opslag
  • Test restore procedure periodiek

Debug & Logging

Huddle logt naar stdout/stderr. Belangrijke log messages:

  • [proxy] listening on :80 — HTTP proxy gestart
  • [api] listening on http://0.0.0.0:3000 — Management API gestart
  • [socket-proxy] container-name → /tmp/dc-sockets/container-name.sock — Socket proxy aangemaakt
  • [socket-proxy] DENY container-name: no active grant — Docker access geweigerd

Veilige log practices:

  • Geen password/secret logging
  • Geen request bodies in logs
  • Redact API response in DEBUG mode only

Veiligheid

Huddle is een high-trust component. Implementatie is gehard tegen de issues uit de eerste security review, maar bevat per ontwerp toegang tot de Docker socket. Houd het volgende aan:

  • Stel Huddle nooit bloot aan onbetrouwbare netwerken — bind 0.0.0.0:3000 alleen op een vertrouwde host
  • Gebruik SECURITY.md (Part B) als regressie-suite na elke wijziging aan api.ts, proxy.ts, socket-proxy.ts of docker.ts
  • Behandel containers als ondertrouw — Huddle staat tussen container en internet, niet andersom

De volledige analyse en het verificatieplan staan in SECURITY.md.
