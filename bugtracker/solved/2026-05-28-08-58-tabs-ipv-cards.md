## Plan: terminal-tab embedden

Doel: in de Terminal-tab een live terminal die een shell opent in de geselecteerde devcontainer (zoals `docker exec -it <name> bash`), volledig binnen het portaal — dus geen lokale terminal nodig.

### Architectuur

1. **Frontend** (Terminal-tab):
   - [xterm.js](https://xtermjs.org/) als render-laag (canvas-based, kleine bundle, ondersteunt resize/copy/paste/colors).
   - WebSocket-verbinding naar een nieuwe huddle-endpoint die rauwe stdin/stdout bytes shuttled.
   - Auto-fit add-on (`@xterm/addon-fit`) zodat de terminal de container-grootte volgt; resize event geeft `{cols, rows}` door over de socket.

2. **Backend** (`gateway/src/`):
   - Nieuwe WS-route `GET /ws/exec/:container` (upgrade-handler via de bestaande `wss`).
   - Auth: dezelfde source-IP check (`isDevcontainerSource`) — devcontainer-netwerken mogen géén exec doen op andere containers. Alleen requests via de host-port `:3000` (admin) zijn toegestaan.
   - Per WS-verbinding één Docker exec-instance:
     1. `POST /containers/:id/exec` met `{Cmd: ["/bin/bash", "-l"], AttachStdin: true, AttachStdout: true, AttachStderr: true, Tty: true, User: "vscode"}` → krijgt `execId`.
     2. `POST /exec/:execId/start` met `{Detach: false, Tty: true}` — geeft een hijacked HTTP-stream terug die bidirectioneel bytes voert (Docker stream-format met TTY=true is rauwe pty, geen multiplexed header).
     3. WS → Docker: alle binary frames doorpipen naar de exec-stream.
     4. Docker → WS: alles wat uit de stream komt direct als binary frame naar WS.
   - Resize: aparte tekst-frame `{"type":"resize","cols":N,"rows":M}` triggert `POST /exec/:execId/resize?h=M&w=N`.
   - Cleanup: WS-close → exec-stream destroy. Een exec zonder open stdin eindigt vanzelf wanneer de shell exit; Docker ruimt de pty op.

3. **Security**:
   - Geen pad-traversal mogelijk: container-naam moet matchen op naam uit `listDevcontainers()` whitelist.
   - Audit: log start/stop van elke exec via `logAudit({container, domain: 'terminal', action: 'open'/'close'})`. Sudo-commando's binnen die shell vallen al onder het bestaande sudo-audit forwarder script in elke container.
   - Default-user `vscode`. `noot` is bereikbaar via `su - noot` in de shell zelf, niet als WS-parameter (anders kan de UI auth bypassen).

4. **Frontend-tab gedrag**:
   - WS pas openen wanneer de Terminal-tab geactiveerd wordt (lazy mount).
   - Bij tab-switch weg: WS open laten (om sessie te behouden tijdens kort weg-klikken naar Firewall), maar `dispose()` op component-destroy.
   - Indicator boven de terminal: "Verbonden als vscode" / "Verbinding verloren — opnieuw verbinden" knop bij socket-close.

### Gefaseerde uitrol

- **Fase 1** — WS-tunnel + xterm.js basic: open shell, lees/schrijf bytes, geen resize, geen reconnect. Genoeg om iets werkends te zien.
- **Fase 2** — resize support, copy/paste, kleurthema-koppeling.
- **Fase 3** — sessie-persistentie (zelfde execId hergebruiken bij reconnect zolang de pty leeft), audit-log integratie, "switch to noot" sneltoets die `su - noot` voorvult.
