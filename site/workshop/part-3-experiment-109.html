Part 3 — Experiment 109

Very experimental VERY EXPERIMENTAL · PUSH THE BOUNDARIES
Docker sandboxes as the main runner

Swaps Docker containers for Docker sandboxes. The least settled of the three. Same path as before, with your own project.

Switch to the experiment

This one is PR #109. Expect rough edges — that is the point of running it.

$ huddle experiment use 109

That one command does three things, in order.

  1. 1
    Writes the channel into ~/.huddle/config.json — channel: experiment, experiment: 109.
  2. 2
    Reinstalls the CLI itself at @infosupport/huddle-cli@experiment-109, then restarts the process. The CLI version is baked in, so it has to hop channels before it can do anything else.
  3. 3
    Runs huddle init with every image tagged experiment-109 instead of latest.

Two commands tell you where you are and get you back:

$ huddle experiment status
$ huddle experiment reset

status prints the CLI version and the active channel (Channel: experiment 109 (images: experiment-109)), and warns when the running CLI does not belong to the configured channel. reset puts the config back on stable and reinstalls the stable CLI.

What you need on the host

Docker or Podman
Same as parts 1 and 2. The gateway still runs as a container.
Docker Sandboxes
Only for the sandbox path: an sbx binary on your PATH. huddle init probes it with sbx version; if it is missing, init prints “(sbx not found on PATH — install Docker Sandboxes to use sbx boxes)” and carries on — devcontainers still work.
A working Docker login
The sbx daemon needs it. Huddle sniffs for that failure and turns it into one message: “Docker login required on the host: run docker login”.
An experiment-109 build
Published per PR by a maintainer. If huddle experiment use 109 cannot install the CLI, the build does not exist yet — that is a finding worth reporting, not something you can fix locally.

Check the sandbox half is usable before you try to create anything:

$ huddle sbx status

It prints the upstream proxy Huddle exposes to sbx, the port, and either sbx: ready — <version> or sbx: unavailable with the reason.

First surprise: Huddle is two processes now

The page title says “sandboxes as the main runner”, and that is the visible half. The other half of #109 is a control-plane / data-plane split, and you will notice it before you get anywhere near a sandbox: the portal has moved to http://localhost:24842.

Huddle Node runs directly on your machine — portal, REST API, SQLite, the CA, devcontainer orchestration, the Docker-socket filter, and everything sbx. huddle-gateway stays in a container and is only the enforcement point. The gateway gets exactly three things from huddle init: where Node is, a token to talk to Node with, and the CA directory read-only. No Docker socket, no database volume, no published portal.

Where each listener lives

The gateway pulls policy and the IP→container map from Node and posts its decisions back. It decides locally, so Node is never in the hot path of a request. If Node is down the gateway keeps enforcing the last policy it received; before the first policy arrives it denies everything.

If everything is blocked, check this first

No policy means deny, never allow. If the gateway container cannot reach Huddle Node on 24843, every environment is denied all egress and nothing appears in the portal to approve — a firewall that looks installed and blocks everything. huddle init probes the channel for real and says which address it picked; docker logs huddle says so too.

Same flow, new foundation

Nothing about the workshop path changes: host runner, gateway, your dev environment, your project. What changes is what your dev environment is — a Docker sandbox instead of a Docker container.

“Instead of” is only half true on this branch. The two runtimes run in parallel and you pick one per environment: the portal's create dialog has an Environment type switch with Sandbox and Devcontainer, and the CLI has a separate command for each. Everything downstream — the firewall rules, the request→approve loop, the network log, the folder mappings — is shared.

Two ways to get a dev environment

A devcontainer is a Docker container on a network with no route off the host, with Huddle wired into it. A sandbox is a Docker Sandboxes microVM: its own kernel, its own filesystem, its own Docker daemon, and egress the host forces through a proxy before the guest gets a say. The trade runs the same way in both directions — the sandbox gives you a much harder isolation boundary and takes away everything Huddle could do inside a container.

PICK THIS ONE WHEN

Take a sandbox when what runs in the environment is an agent you would rather not have on your machine, and you can live without snapshots and a fully wired IDE. Take a devcontainer when you want the part 1 experience — per-container Docker permissions, non-root, snapshots, an IDE that attaches.

Path A — how a devcontainer is wired

Unchanged in shape from part 1, and worth having next to path B. The container is put on a per-container --internal network with no route to the internet of its own, and the gateway is the only other member. Inside the container, iptables DNATs all outbound tcp/80 to the gateway, accepts loopback and the gateway, and drops everything else — so it fails closed inside the container too.

Path B — how a sandbox is wired

Nothing about the sandbox's own networking is Huddle's to build. Docker Sandboxes already forces every outbound connection from the microVM through a proxy on your host, deny-by-default, with non-HTTP protocols blocked — and it does that outside the guest, so root inside the VM cannot get around it. Huddle plugs in as that proxy's upstream.

Two consequences fall straight out of that picture, and they are the reason this path needed a design of its own.

  1. 1
    Huddle never talks to the sandbox. It talks to the host-side sbx daemon, which terminates and rewrites everything the box sent. A header, an env var or a client cert set inside the box does not survive the trip, and every sandbox on the machine arrives on one socket from one address.
  2. 2
    The upstream proxy setting is global to the sbx daemon. There is no per-sandbox override: sbx settings set proxy.sandbox <url> is one setting for the whole machine.

So how does the gateway know which box is calling? That is the next section, and the most interesting thing on this branch.

Mounts
Every folder is a positional on sbx create and lands at its own host path inside the VM. On Windows that means the MSYS form: T:\projects\huddle is /t/projects/huddle in the sandbox. At most 32 folders per sandbox.
Read-only
sbx's own :ro suffix, on extra folders only. The first folder — the one the agent starts in — can never be read-only, so the portal hides the toggle on that row.
Docker policy
None. The socket proxy and the per-action grants are a devcontainer mechanism; the VM boundary replaces them.
TLS
Huddle's CA is installed twice: inside the sandbox (so HTTPS and editor backends work) and on the host, because sbx terminates TLS itself for some destinations and then validates Huddle's certificate against the host trust store. Without the host half you get Empty reply from server / ECONNRESET and nothing useful in the log.
Snapshots
There is no sbx equivalent of docker commit, so the Snapshot action is not offered for a sandbox.

The interesting bit: how the gateway knows which sandbox is calling

One thing survives the host daemon's rewriting: the credential in the upstream-proxy URL. Not by luck, but structurally — it is the hop's own authentication, what the daemon must present to get through the proxy at all. Something that has to survive for the connection to work cannot be stripped.

And the setting being global turns out not to matter, because of when sbx reads it: the URL is baked in when the sandbox is created. Setting it immediately before each create is therefore a per-sandbox injection.

Create-time: mint, inject, bake, park
1 · Mint
Huddle Node makes a fresh 256-bit secret for this box and stores it with the name. The gateway is given only the SHA-256.
2 · Inject
sbx settings set proxy.sandbox http://<name>:<secret>@localhost:32768
3 · Bake
sbx create — the box keeps the URL it was created with, measured to hold across a restart.
4 · Park
The global setting goes back to huddle-unclaimed — a credential that maps to no sandbox. Anything turning up holding it is denied by name instead of inheriting the last box's rights.

Creates are serialised for the same reason: one global setting plus set-then-create is a race, and two starts in flight could hand both boxes the same identity or swap them.

On every request, upgrade and CONNECT arriving on 32768, the gateway reads Proxy-Authorization, matches the secret's hash in constant time, strips the header before forwarding, and then runs the same rule check a devcontainer takes — with the sandbox's name where a container id would be. That is what makes a sandbox a first-class rule scope: a blocked domain files a requested row against the box that asked for it, and path rules work per sandbox, which sbx's own policy engine cannot express.

Which is why the reconciler now does something surprisingly small. Huddle-managed sandboxes are set to allow-all in sbx — one allow * rule each — and every decision is taken at Huddle's proxy. One policy engine, one audit trail, one place to approve a domain. Sandboxes Huddle did not create are left alone; widening their policy is not Huddle's to do.

There is nothing behind the gateway any more

With sbx on allow-all, the gateway's “no” is the only thing between a sandbox and the internet — including when the gateway is down or its policy feed is stale. An unknown or absent credential is denied outright, and the 403 says which case it is: no credential at all, the unclaimed credential, or a name the gateway does not know. If you see one of those, the move is to recreate the sandbox from Huddle.

Creating a sandbox

In the portal

  1. 1
    Open http://localhost:24842 — huddle init prints an auto-login link with the operator token in it.
  2. 2
    Dev Environments in the sidebar, then Create dev environment.
  3. 3
    Under Environment type, pick Sandbox. The bullets under it change to MicroVM isolation · Docker runs inside the VM · Runs as root, so the consequence of the choice is on screen.
  4. 4
    Name is optional — leave it blank and you get an auto name (huddle-sbx-…).
  5. 5
    Project folders: add at least one, or the dialog refuses with “Add at least one folder”. The first folder is where the agent starts. The destination field is disabled for a sandbox, with the reason in its tooltip: “Sandboxes mount every folder at its own host path — this can't be changed here.” Use Add folder, or its chevron → Browse… to pick from a host folder dialog. The read-only toggle is the pen/eye icon button, and it is hidden on the first row.
  6. 6
    Your folder mappings (Settings → Folder mappings) are listed as “Settings folders mounted automatically” before you create anything — and so is anything that cannot travel, under “Not available in a sandbox”. Docker volume mappings and ~-paths end up in that second list.
  7. 7
    Right-hand column, Dev environment settings: the Agent accordion (claude by default), Environment variables (containerEnv / remoteEnv), IDE, Customisations, Lifecycle commands. The same column a devcontainer gets.
  8. 8
    Start environment. On failure the dialog shows the first command that broke, verbatim — with the credentialed URL redacted in what it prints.

The new environment then appears in the Dev Environments table with type Sandbox, its SSH host (<name>.sbx) under the name, its count of pending firewall requests, and a Detail button. Start and Snapshot are container-only; a sandbox row offers Detail and Delete.

From the CLI

One folder, then one folder plus a read-only second:

$ huddle sbx start my-box --workspace /home/you/projects/myrepo
$ huddle sbx start my-box --workspace /home/you/projects/myrepo --folder /home/you/projects/mylib:ro
[name]
Positional, or --name <name>. Omit it and the API generates huddle-sbx-<base36>.
--workspace <path>
The folder the agent starts in.
--folder <path>[:ro]
An extra folder. Repeatable. :ro mounts it read-only.
--agent <name>
The CLI agent that runs inside the sandbox; claude by default.

Output is one line per step — set sandbox upstream proxy → Huddle, create sandbox, reset sandbox upstream proxy → unclaimed, install Huddle CA in sandbox (TLS trust), link settings folders — each with its exit code and the command that ran. That step list is the debugging surface for this path: read it top to bottom and stop at the first non-zero.

The rest of the group:

$ huddle sbx list
$ huddle sbx ssh-setup
$ huddle sbx trust-ca my-box
$ huddle sbx trust-host
$ huddle sbx reconcile --dry-run
$ huddle sbx log my-box
$ huddle sbx rm my-box --force
ssh-setup
Runs sbx's SSH setup once, so an editor can connect to <name>.sbx. The /sandboxes page turns that into deep links for VS Code Remote-SSH and JetBrains Gateway.
trust-ca <name>
Reinstalls Huddle's CA inside one sandbox and refreshes its trust store. Reconnect your editor afterwards.
trust-host
Trusts Huddle's CA on the host, where the sbx daemon runs. huddle init already does this when sbx is installed; it is idempotent.
reconcile
Re-asserts the one allow * rule per Huddle-managed sandbox and clears what the old projection left behind. It also runs on its own — debounced on rule changes, and on a timer. --dry-run shows what it would do.
log <name>
Dumps sbx's own policy log as raw JSON plus whatever Huddle parsed out of it. A diagnostic — with sbx on allow-all it should have nothing to say about a Huddle box.
rm <name>
Removes the microVM. The identity row is dropped whatever the exit code — a box does not outlive its credential.

From the CLI

$ huddle start --ide vscode --workspace /home/you/projects/myrepo
--ide
intellij (default), rider or vscode.
--workspace <path>
Defaults to the current directory. huddle with no arguments, or huddle <folder>, is the same thing.
--mount <host>=<container>
Mount a host folder at an absolute container path. Repeatable; cannot be combined with --workspace or --empty. This is the flag with no sandbox equivalent.

Which container path the IDE opens as project root when using --mount.

The thing #109 really changes here is where the command lands: huddle start now talks to Huddle Node on http://localhost:24842, not to the container on :3000. If a huddle command reports that Huddle does not appear to be running, that is the split, not your project — check both halves:

$ huddle logs -f

Shows both — Node's log file on this host (~/.huddle/node.log) and the gateway container. --node or --gateway narrows it to one half, -n <lines> sets the count. To watch Node in the foreground instead, huddle node.

Where it is rough

The branch says so about itself, which is useful: you can tell a new finding from one that is already written down. Everything below comes from the branch — a TODO in the code, an open question in an ADR, or a control the UI disables on purpose.

IDE attach
Validating a JetBrains Gateway / VS Code attach into a sandbox is still an open item. The JetBrains plugins and settings you enter are written into the sandbox but never applied — there is no backend process in a bare sandbox to apply them to. The file is written in the shape a future attach would look for.
postAttachCommand
Runs once at create for a sandbox, because there is no attach event to observe.
sbx verbs Huddle guesses at
The SSH setup verb and the per-sandbox policy scope flag are both marked in the code as unconfirmed guesses against the real sbx CLI. If ssh-setup or reconcile fails with a usage error, that is why.
The policy-log parser
Best-effort. huddle sbx log says so outright: “(parser matched nothing — paste the raw JSON above so the parser can be tuned)”.
Restart paths
The credential surviving a restart is measured, not assumed — but sbx has stop and no start, and a machine reboot has not been exercised. That is what the park-on-unclaimed step exists to make safe: the failure mode is a readable denial, not a box passing for another one.
Name collisions
A sandbox and a devcontainer share one keyspace for rule scoping, and a sandbox name is drawn from roughly the same character class as a Docker container name. Nothing currently stops them colliding; the code flags it rather than hiding it.
Slimming the gateway
Partial. The mounts are gone and the process no longer loads the database, the Docker code or the API — but the image still ships every source file.
Stale labels
huddle sbx status still prints “host-agent socket”, from the file-mailbox bridge this branch deleted. Cosmetic, but it will confuse you if you go looking for a socket.
Docs that disagree
The branch's own AGENTS.md, the /sandboxes page and the older ADR still describe the superseded model, where Huddle mirrored its ruleset into sbx and sbx enforced per box. The code does the opposite now: sbx is allow-all and Huddle decides everything. Trust the code.
