Very experimental VERY EXPERIMENTAL · PUSH THE BOUNDARIES
Docker sandboxes as the main runner

A sandbox instead of a container as your dev environment. Two short steps: create one, connect to it.

Read this first: this one is properly unfinished

This is the least settled of the three parts by a wide margin. It is an open pull request, not a release, and it is not one small change — it swaps the foundation your dev environment runs on and moves half of Huddle to a different process. Things are missing, half-wired, and in places documented wrong on the branch itself.

That is what you are here for. Do not try to work around a problem quietly — a thing that breaks is the output of this part. Write it down and put it on the PR.

Do not do this on anything you care about, and do not expect to get real work done in a sandbox today.

STEP 1

Switch to the experiment

$ huddle experiment use 109
THE PORTAL MOVES

This branch splits Huddle in two, so the portal is no longer on :3000. It is on http://localhost:24842. huddle init prints an auto-login link with the right address — use that link rather than a bookmark, or you will think it is broken.

Check where you are, and get back out, with:

$ huddle experiment status
$ huddle experiment reset
$ huddle sbx status

huddle sbx status is the one to run before anything else: sandboxes need the sbx tool on your host, and this says whether Huddle can see it.

STEP 2

Create a sandbox

  2. 2
    Set Environment type to Sandbox — that is the choice that matters here.
  3. 3
    Give it a Name, and add your project under Project folders with Add folder.
  4. 4
    Press Start environment.

  1. 1
    Name the sandbox and point it at your project.
  2. 2
    Add more folders with --folder, repeatably; append :ro for read-only.
  3. 3
    Check it came up with huddle sbx list.
$ huddle sbx start my-box --workspace /home/you/projects/myrepo
$ huddle sbx list
$ huddle sbx rm my-box --force

A devcontainer is still huddle start, exactly as in part 1.

STEP 3

Connect to the sandbox

Connecting goes over an SSH bridge, which has to be switched on once. After that the sandbox answers as <name>.sbx and your IDE connects to it as a remote host.

$ huddle sbx ssh-setup
$ huddle sbx trust-ca my-box
$ ssh my-box.sbx

trust-ca installs Huddle's CA inside the sandbox, which the VS Code and JetBrains backends need before HTTPS works. Then connect from your IDE the way you would to any remote host over SSH.

Once you are in, it is the same workshop as part 1: run your project, watch requests arrive, approve them.

Known issues — so you can tell a new one from an old one

All of this is already known. If you hit something that is not on this list, that is the interesting one.

  • IDE attach is unfinished. The branch says so itself. Expect the SSH route to be fiddly, and expect JetBrains to be worse off than VS Code.
  • A sandbox has one layer of enforcement, not two. Huddle sets its own sandboxes to allow-everything in sbx and enforces the rules at its own proxy instead. If a sandbox reaches the internet without Huddle in the path, nothing stops it.
  • The portal address changed to :24842, and anything pointing at :3000 will look dead.
  • No snapshots for sandboxes. The portal only offers that for devcontainers.
  • Restarting is not really a thing yet. A sandbox can be stopped, but starting a stopped one back up is not wired, and surviving a reboot is untested. Expect to remove and recreate.
  • The old Sandboxes page is stale. It is no longer linked from the sidebar or the dashboard but is still reachable, and the status it shows cannot be trusted. Use Dev Environments.
  • JetBrains customisations are recorded but not applied.
  • The docs on the branch contradict the code in places — AGENTS.md and some ADRs still describe an earlier design. Trust the behaviour, not the prose.
  • The experiment build may not exist yet. Publishing it is a manual, maintainer-only step, so huddle experiment use 109 can fail through no fault of yours. Say so if it does.
Findings

What broke, confused you, or behaved differently than expected? That's a finding, not your fault. Write it down.
