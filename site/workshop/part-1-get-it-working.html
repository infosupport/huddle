Part 1 — Get it working

Latest release STABLE · GET THE BASICS WORKING

Install the CLI, connect to an empty container and watch how firewall requests surface and get approved. Then bring your own project in and start it inside the dev container.

Everything on this page is the latest release. Nothing here needs an experiment channel — that is what parts 2 and 3 are for.

Setup

Two commands on your own machine. The CLI is the host runner — it starts the gateway and holds an ephemeral operator token.

$ npm install -g @infosupport/huddle-cli
$ huddle init

Before you run it

Node
18 or newer — the CLI package declares node >=18.
Container runtime
Docker or Podman, running and reachable. huddle init auto-detects: it looks behind the docker command first (which may be a Podman shim), then at podman. Force one with --runtime docker, --runtime podman or the HUDDLE_RUNTIME env var.
Host port
The portal is published on 3000. Set HUDDLE_PORT before huddle init to publish it on another host port.
Nothing else
No IDE plugin, no manual network or volume setup. huddle init creates the volume huddle-data, the internal network devcontainer-net and the socket directory /tmp/dc-sockets itself.

If no runtime is up you get told so, and told what to do: “No working container runtime found. Install and start Docker or Podman, or pick one explicitly with --runtime <docker|podman> or the HUDDLE_RUNTIME env var.”

What it looks like when it worked

Check the install with huddle --version. Then huddle init pulls the images, starts the gateway and ends with a link that logs you straight in — the portal reads the ?token=, logs in, and removes it from the address bar.

$ huddle --version
$[OK] Huddle is running at http://localhost:3000
$Open the portal (auto-login link):
$    http://localhost:3000/?token=<operator-token>

The same token is written to ~/.huddle/config.json, which is how later huddle commands authenticate. Re-running huddle init reuses the token from that file, so an open browser tab keeps working across a re-init.

The architecture, in detail

The whole design rests on one property: the gateway is the only container that is a member of two kinds of network at once. Your dev container sits on an internal network, which has no route to the internet of its own. The gateway sits on that same internal network and on the engine's default bridge network, which does have a route out. So the gateway is not the recommended way out — it is the only way out.

Three networks, and who is on them

huddle init creates one shared internal network up front. The gateway then creates one more internal network per dev container, and joins that one itself as well.

NetworkCreated byInternal?Who is on it
bridge (Docker) / podman (Podman) The engine itself No — this is the route out The gateway, plus whatever else you run on your machine.
devcontainer-net huddle init, with network create --internal Yes The gateway. This is the network huddle migrate points an existing Compose devcontainer at.
dc-net-<container-name> The gateway, on every container start (Internal: true) Yes One dev container, plus the gateway. Each container gets its own, so containers cannot see each other either.

Because the gateway is on the container's own network, ordinary container DNS resolves the name huddle from inside it. That is why every proxy setting can just say http://huddle:80 and no IP address is ever baked in.

WHY THE ORDER MATTERS

Docker skips the host port-forward entirely when a container is created directly on an --internal network (moby/moby#36174). So the gateway is started on the engine's default network with -p, and joins the internal networks afterwards. Do it the other way around and the portal is simply unreachable on localhost:3000. Which source IP the gateway then sees for forwarded traffic no longer matters, because the control plane authenticates with the operator token rather than by source IP.

It fails closed twice

The network boundary is the first mechanism. The container's own network stack is the second: the gateway installs iptables rules inside each container when it starts, so even a process that ignores http_proxy gets nowhere.

At the gateway

The proxy on :80 looks the destination up in the rule table. No matching rule means the host is filed as requested and the connection does not go through. Nothing is allow-listed by default — a fresh database holds exactly one allow rule, for the gateway's own name.

allowdenyrequested → blocked
At the container

The container is started with NET_ADMIN so the config script can write its own OUTPUT chain. Port 80 is redirected to the gateway, loopback and the gateway are accepted, and every other TCP packet is dropped.

$HUDDLE_IP=$(getent hosts huddle | awk '{print $1}')
$iptables -t nat -A OUTPUT -p tcp --dport 80 ! -d "$HUDDLE_IP" -j DNAT --to-destination "$HUDDLE_IP:80"
$iptables -A OUTPUT -o lo -j ACCEPT
$iptables -A OUTPUT -p tcp -d "$HUDDLE_IP" -j ACCEPT
$iptables -A OUTPUT -p tcp -j DROP

Those rules name the gateway by IP, so they go stale if the gateway container is recreated. That is why the gateway rebuilds them itself, for every container it finds, on startup.

Two more things the boundary needs

TLS interception
The gateway terminates HTTPS with its own CA, so it can see host and path instead of an opaque tunnel. (A domain named in the gateway's NO_INTERCEPT_DOMAINS keeps a raw tunnel instead, for clients that pin certificates; that list is empty unless you set it.) Interception only works if the container trusts that CA, so the CA lands in the system trust store and in three env vars set on the container itself — NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and REQUESTS_CA_BUNDLE. On the container rather than in /etc/profile.d alone, because tools the IDE starts do not run a login shell.
The Docker socket
A dev container that can talk to the real Docker socket could start a container outside the boundary. So each container gets its own filtered socket instead: the gateway runs a per-container socket proxy under /tmp/dc-sockets/<container-name>, bind-mounts that directory to /var/run/huddle, and points DOCKER_HOST at it. The proxy stamps every request with an X-Container-Id header, which is what the policy layer decides on. The directory rather than the socket file is deliberate: a file bind pins the inode, so after a gateway restart it would point forever at a dead socket.

Create an empty container

An empty container is a dev container without a workspace: no folder from your machine is mounted, and no worktree is created for it. You get a running container with the base image, the proxy environment and the filtered Docker socket — and you clone into it by hand. It is the cleanest way to see the firewall loop, because nothing of yours is in the way.

There are two ways in, and they do the same thing: both end in a POST /api/docker/start with empty: true. Use whichever you prefer.

Option A — in the portal

Start devcontainer
  1. 1
    Open the portal. The auto-login link huddle init printed logs you straight in; otherwise go to http://localhost:3000 and paste the operator token.
  2. 2
    Press Start devcontainer. There are three of those buttons: on the Containers page (top right), on the Dashboard in the orange “Huddle! We've got your back.” banner, and as the + icon in the top bar.
  3. 3
    In the Start devcontainer dialog, pick your IDE: IntelliJ IDEA, Rider or VS Code. This choice drives everything below it, so set it first.
  4. 4
    Pick an Image. The list holds the default base image for that IDE, shown as [Default] ghcr.io/infosupport/base-devimage-<ide>, plus any snapshots you made earlier as [Snapshot] <name> (<size>). The default is pre-selected.
  5. 5
    Tick Empty (clone manually). The Workspace directory field is cleared and disabled, and — as long as you have not typed a name yourself — Container name is filled in with devcontainer-empty.
  6. 6
    Change Container name if you want more than one empty container. The name has to be free: a name that is already taken comes back as “Container '<name>' already exists”.
  7. 7
    Press Start. The dialog shows Starting container…, then closes and the container list reloads. Image and container name are required, and the workspace is required unless Empty is ticked — otherwise you get “All fields are required”.

Without Empty, typing a workspace path auto-fills the container name as devcontainer-<last path segment>, and it keeps doing that until you edit the name yourself. That is the same naming rule the CLI uses.

Option B — from the CLI

huddle start --empty
$ huddle start --empty
$Starting devcontainer-empty with intellij...
$Image: ghcr.io/infosupport/base-devimage-intellij
$[OK] Container started: devcontainer-empty (a1b2c3d4e5f6)
$Open in JetBrains Gateway: Remote Development > Dev Containers -> devcontainer-empty

With --empty the CLI does not look at your working directory at all. The container name defaults to devcontainer-empty, and the image comes from GET /api/docker/base-image?ide=<ide> unless you passed --image.

The options that apply here, straight from huddle --help:

--empty
Empty container without a workspace.
--ide <intellij|rider|vscode>
IDE (default: intellij).
--name <name>
Container name (default: devcontainer-<foldername>, so devcontainer-empty here). It has to start with a letter or digit and may then contain letters, digits, _, . and -; anything else is refused with “Invalid container name”.
--image <image>
Use a specific image instead of the IDE's base image.
--url <url>
Huddle URL (default http://localhost:3000, or the HUDDLE_URL env var) — for when you published the portal on another port.

A fuller example, and the short form: start may be left out entirely, because a first argument that is not a known command falls through to start.

$ huddle start --empty --ide vscode --name devcontainer-scratch
$ huddle --empty

If the CLI cannot reach the API it says so, and points at the fix: “Huddle does not appear to be running. Start it with: huddle init”.

Then attach your IDE

The container itself runs nothing: its entrypoint is /bin/sh -c 'while sleep 1000; do :; done'. It idles, and your IDE attaches to it and installs its own backend.

VS Code

Run Dev Containers: Attach to Running Container and pick the container by name.

IntelliJ IDEA / Rider

In JetBrains Gateway: Remote Development > Dev Containers, then the container by name. The CLI also waits three seconds and prints a Gateway-link: line if the backend is far enough along to hand one out. That is best-effort, so its absence does not mean anything is wrong.

What you end up with

All of this comes from the container start, whichever of the two ways you used.

Name
devcontainer-empty, unless you named it something else.
Network
dc-net-devcontainer-empty, internal, created on the spot; the gateway joins it too.
Image
ghcr.io/infosupport/base-devimage-<ide>, or your snapshot. If the image is not present locally, the gateway first builds it from the bundled Dockerfile for that IDE.
Entrypoint
/bin/sh -c 'while sleep 1000; do :; done' — it idles until an IDE attaches.
Memory / CPU
8g and 2 CPUs by default (a CPU quota against a 100 000 µs period). Change the defaults under Resource limits on the portal's Settings page — Default memory (e.g. 4g, 2048m) and Default CPU (e.g. 2, 0.5).
Capabilities
NET_ADMIN, so the config script can install the container's own iptables rules.
Proxy env
http_proxy, https_proxy, HTTP_PROXY and HTTPS_PROXY, all set to http://huddle:80.
No-proxy env
no_proxy and NO_PROXY set to localhost,127.0.0.1,::1,[::1]. The bracketed [::1] is in there on purpose: .NET/Aspire's DCP addresses its targets as http://[::1]:<port> and matches NO_PROXY literally against that bracketed host.
CA env
NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/huddle-ca.crt, SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt and REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt.
Docker access
DOCKER_HOST=unix:///var/run/huddle/docker.sock, backed by the bind mount /tmp/dc-sockets/<name> → /var/run/huddle. The config script also symlinks the default socket path to it, for tools that ignore DOCKER_HOST.
Mounts
That socket directory, whatever is switched on under Folder mappings on the Settings page (a host path gives a bind mount, a volume name gives a Docker volume), and for the JetBrains IDEs the shared RemoteDev volume. No workspace bind mount — that is the whole point of empty.
Workspace
None. No worktree is created, and the IntelliJ sources-path label is left empty, so the IDE does not open a project for you.

Outcome: an idling container behind the boundary, with nothing allow-listed. Your first git clone in it is the first firewall request you approve.
