Part 1 — Get it working

Latest release STABLE · GET THE BASICS WORKING

Set up once, then three steps: an empty container, your own project, and running that project inside the dev container. Every step works from the portal or from the CLI — pick either.

Setup

Two commands on your own machine. Then you are done with setup and the three steps begin.

$ npm install -g @infosupport/huddle-cli
$ huddle init
$[OK] Huddle is running at http://localhost:3000
$Open the portal (auto-login link):
$    http://localhost:3000/?token=<operator-token>

Open that link and you are logged in — the portal reads the ?token= and strips it from the address bar. The same token lands in ~/.huddle/config.json, which is how later huddle commands authenticate.

You need
Node 18+, and Docker or Podman running. huddle init auto-detects the runtime; force it with --runtime docker|podman or HUDDLE_RUNTIME.
It creates
The volume huddle-data, the internal network devcontainer-net and the socket directory /tmp/dc-sockets. No IDE plugin, no manual setup.
Another port
Set HUDDLE_PORT before huddle init — and set HUDDLE_URL=http://localhost:<port> too, keeping it set for every later huddle command. HUDDLE_PORT only decides where the gateway is published; the CLI still talks to http://localhost:3000 unless HUDDLE_URL or --url says otherwise, so setting just the one leaves every command afterwards pointed at the wrong port.

How it is put together

Your dev container sits on an internal network with no route to the internet. The gateway sits on that network and on the engine's bridge network, which does have one. So the gateway is not the recommended way out — it is the only way out.

The three steps

Setup is done. From here it is three blocks of work, each one doable from the portal or the CLI.

  1. 1
    An empty container. Create it, connect to it, and watch the first firewall requests arrive.
  2. 2
    Bring your own project in. Same thing, pointed at a folder on your machine.
  3. 3
    Start your project inside the container. Build it, run it, approve what it needs.

Outcome: your actual work runs in Huddle, and you know which of your dependencies needed rules.

STEP 1

An empty container

A dev container with no folder from your machine mounted: base image, proxy environment, filtered Docker socket — and nothing in it but the base image. Nothing of yours is in the way, so the firewall loop is easy to see.

  1. 1
    Press Start devcontainer — on the Containers page, in the dashboard banner, or the + in the top bar.
  2. 2
    Fill the dialog as below. Set IDE first: it drives the image list.
  3. 3
    Press Start. It shows Starting container…, then closes and the list reloads.

    Run the command. --empty is what makes it empty; --ide picks the IDE and its base image.
  2. 2
    The name defaults to devcontainer-empty — add --name for more than one.
  3. 3

$ huddle start --empty

--empty
No workspace. Your working directory is not looked at.
--ide
intellij (default), rider or vscode.
--name
Defaults to devcontainer-empty. Must start alphanumeric, then letters, digits, _, ., -.
--image

start is optional — huddle --empty does the same, because a first argument that is not a known command falls through to start.

Connect to it

Attach your IDE, open a terminal inside the container and run one curl. That single request is the whole loop: nothing is allow-listed up front except the gateway's own name, huddle, so this one has to be approved before it goes anywhere.

$ curl https://infosupport.github.io/huddle/api/hello.json
${
$  "ok": true,
$  "message": "You got your first curl working in Huddle.",
$  ...
$}

The first run fails straight away — 403 from the proxy on the CONNECT, because the rule it just raised is still pending. Nothing is waiting for you: approve infosupport.github.io on the Firewall page, then run the same curl again and it returns the JSON. That failure is the exercise, not a mistake.

No -x and no -k are needed: the container already has http_proxy pointing at huddle:80 and the gateway's CA in its trust store, so an ordinary curl is routed and trusted with no flags from you.

Attach

VS Code: Dev Containers: Attach to Running Container.
JetBrains: Gateway → Remote Development > Dev Containers. The CLI also prints a Gateway-link: when the backend is ready enough — best-effort, so its absence means nothing.

Approve

Requests land on the Firewall page under Pending requests, each row with Allow Allow globally Temp 5 min Path mode Deny. Or walk the queue with huddle fw list -i.

Done when: you approved a request you caused yourself, and the JSON came back.

STEP 2

Bring your own project in

Same container, pointed at a folder on your machine.

  1. 1
    Press Start devcontainer again and pick your IDE and Image as before.
  2. 2
    Leave Empty unticked and type the host path into Workspace directory, e.g. C:/projects/my-project.
  3. 3
    Press Start.
Start devcontainer
Empty (clone manually)Leave it unticked this time.
Workspace directoryThe host path to your project. Required — without it you get “All fields are required”.
Container nameAuto-fills as devcontainer-<last path segment> while you type, until you edit it yourself.
  1. 1
    Run it from inside your project — with no --workspace the CLI uses the current directory.
  2. 2
    Or name the folder explicitly, as a flag or as a bare argument.
  3. 3

$ huddle start
$ huddle start --workspace /home/you/projects/my-project --ide vscode

A path that does not exist, or is not a directory, is refused before anything starts.

Where your code lands

In the container
/workspaces/<last segment of your path> — so C:/projects/my-project shows up as /workspaces/my-project.
On your machine
The worktree at <your-repo>/.worktrees/<container-name>, on branch worktree/<container-name>. Reused if it already exists.
Your checkout
Untouched. Same repo, different working tree.

Done when: your IDE opens your project from inside the container.

STEP 3

Start your project inside the container

Now run it: restore packages, build, test, start. This is the part that produces findings, because your project reaches for hosts nobody allow-listed yet — and each one stops until you approve it.

Expect the requests roughly in this order: your package registry first (npm, NuGet, Maven, PyPI), then whatever your build downloads at runtime, then anything your app talks to when it starts.

  1. 1
    Run your build in the container's terminal. It will stall on the first blocked host.
  2. 2
    Open Firewall → Pending requests and approve from the row menu: Allow for this container, Allow globally for every container, Temp 5 min to try something out.
  3. 3
    Re-run the build. Repeat until it is green — the list of rules you accumulated is the answer to “what does my project actually reach for”.

For a shared registry, prefer Path mode over allowing the whole host: it blocks the host at the root and passes only the paths you list. That is the subject of part 2.

  1. 1
    Run your build in the container's terminal.
  2. 2
    Walk the queue interactively from your own machine and answer each one.
  3. 3
    Re-run the build. Repeat until green.
$ huddle fw list -i
$ huddle firewall list --container devcontainer-my-project
$ huddle firewall add registry.npmjs.org

--status filters the list (requested by default), and --path on add takes a pattern instead of the whole host.

When your project needs more than rules

More memory or CPU
Containers get 8g and 2 CPUs by default. Change it under Resource limits on the portal's Settings page — Default memory and Default CPU.
Caches from your machine
Folder mappings on the Settings page mount extra folders into every container: a host path becomes a bind mount, a volume name becomes a Docker volume ({containerName} in the name expands per container). Handy for a package cache you would rather not download twice.
Docker from inside
Already wired: DOCKER_HOST points at the filtered socket, so docker and Compose work. Every call carries the container's identity, so Docker access stays policy-controlled.
A port to your browser
Your app listens inside the container — reach it the way your IDE's port forwarding exposes it.
