One ruleset, shared across the team

In part 1 you approved every host your project needed. Your teammates would have to do all of that again. This part makes that ruleset a thing your team owns, keeps in Git, and applies to any container.

Switch to the experiment

$ huddle experiment use 98

This is PR #98 — a pull request, not a release, and it carries other work besides rule sharing. huddle experiment status shows where you are; huddle experiment reset puts you back on the stable build.

How the sharing works

Rules become a group: a named set with a description, which exports to a single JSON file. That file is the unit you commit to Git. Point every teammate's Huddle at that folder and the group loads on its own.

Applied globally or per container

Applying a group is what puts it in force — globally, or on one container. The rules stay part of the group, so it can be re-applied or removed as a unit.

STEP 1

Group your rules and export them

  1. 1
    Open Firewall. The panel is Firewall rules & groups.
  2. 2
    Press New group and name it after what it is for — NPM Registry, GitHub, your project.
  3. 3
    Put the rules you approved in part 1 into it, then press Export to download the group as JSON.

A group marked Shared is one meant for the team. All rules and Ungrouped export too, but those come out as a plain rules file rather than a group.

  1. 1
    See what groups exist.
  2. 2
    Export one to a file — that file is what you commit.
  3. 3
    Or export the flat ruleset for one container, or for the global scope.
$ huddle firewall group list
$ huddle firewall group export "NPM Registry" --out npm-registry.json
$ huddle firewall export --container devcontainer-app --out app-rules.json

Without --out the JSON goes to stdout, so you can pipe it. Use --container __global__ for the global scope.

What a group file looks like

Small enough to review in a pull request, which is the point.

{
  "version": 1,
  "kind": "huddle-firewall-group",
  "group": { "name": "NPM Registry", "description": "…", "shared": true },
  "rules": [
    { "domain": "registry.npmjs.org", "status": "deny",  "path_pattern": null,          "path_mode": 1, "container_id": null, "expires_at": null },
    { "domain": "registry.npmjs.org", "status": "allow", "path_pattern": "/@angular/*", "path_mode": 0, "container_id": null, "expires_at": null }
  ]
}
domain
The host. *. wildcards allowed.
path_pattern
A path, or null for the whole host. * matches within a segment; a trailing * spans deeper.
path_mode: 1
Marks the host a path-allowlist: blocked at the root, only the listed paths pass.
container_id
null is global; otherwise one container.
STEP 2

Put it where the team can reach it

Commit the file to a folder in a repo everyone has — then point Huddle at that folder. Groups in it load on start and on every reload, with a From folder badge.

  1. 1
    On Settings, under Team-managed defaults, set the Firewall rules folder to your checkout.
  2. 2
    Restart Huddle so it can actually see that folder.
  3. 3
    Press Reload to re-read it, or Sync to folder on the Firewall page to write your groups back out as files.
  1. 1
    Set the folder. This only records the path.
  2. 2
    Restart, which mounts it into the gateway. Without this the folder is invisible to Huddle.
  3. 3
    reload reads files into Huddle; sync writes Huddle's groups back out as files.
$ huddle firewall folder set /path/to/firewall-rules
$ huddle restart
$ huddle firewall folder reload
$ huddle firewall folder sync

sync writes stable 2-space JSON with a trailing newline, so the diffs stay readable in Git.

The folder owns only what it loaded
Rules you added by hand survive a reload. It does not take over your own work.
One bad file breaks nothing
Reload validates every file before it touches live policy, and aborts wholesale if any of them is broken — so a bad commit cannot wipe the team's rules.
STEP 3

Apply it to a container

Loading a group makes it available. Applying it makes it take effect — pick global, or one container.

  1. 1
    On Firewall, find the group. A teammate's file shows a From folder badge; a file you were handed goes in with Import.
  2. 2
    Choose a scope next to Apply to — Global, or a specific container.
  3. 3
    Press Apply. Rules already in that scope are refreshed and adopted into the group.
  1. 1
    Import a file you were handed, if it is not coming from the folder.
  2. 2
    Apply the group globally, or to one container.
  3. 3
    Check the result with huddle firewall list --status allow.
$ huddle firewall group import npm-registry.json
$ huddle firewall group apply "NPM Registry"
$ huddle firewall group apply "NPM Registry" --container devcontainer-app

Hand a group file to huddle firewall import by mistake and it routes it to the group importer for you, rather than silently dropping the group.

Done when: a teammate's container has your rules without anyone approving them a second time.

Two things worth knowing before they bite you

Merge vs replace

Import merges by default: existing rules are updated, new ones added. --replace wipes the scopes you are importing first — not the whole table. Combined with --container it clears that scope even from an empty file, so “import nothing to clear it” genuinely clears it instead of quietly doing nothing.

Whole host, or paths

For something you talk to, allow the host. For a registry everyone pulls their own things from, use path mode: block the root, allow only the scopes you need. A compromised build then cannot pull arbitrary packages from the same host. The examples in examples/firewall-rules/ show both.
