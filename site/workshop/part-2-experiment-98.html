Experimental EXPERIMENTAL · TRY SOMETHING NEW
Export and import firewall rules

Export the ruleset you built up in part 1, then import it somewhere fresh. Rules travel as a JSON document — either as a flat list, or as a named group your team keeps in Git.

Switch to the experiment

Experiments are opt-in builds of the CLI. This one is PR #98.

$ huddle experiment use 98

That one command swaps out both halves of Huddle. It writes the channel and experiment: 98 into ~/.huddle/config.json, reinstalls itself globally as @infosupport/huddle-cli@experiment-98, restarts the process, and then runs huddle init with the experiment-98 images. CLI and images therefore always run the same build.

If that install fails, the CLI puts the two config keys back the way they were — so your next huddle init is not stuck on a build that cannot be installed.

Confirm what you are on, and get back to the released CLI when you are done:

$ huddle experiment status
$ huddle experiment reset

status prints the CLI version and the channel; on this experiment that reads Channel: experiment 98 (images: experiment-98). It also warns when the running CLI does not belong to the configured channel — the next huddle init fixes that by itself. reset removes the experiment from the config, reinstalls the stable CLI and puts you back on the latest images. Until you run it the experiment stays active, including across huddle init.

A PULL REQUEST, NOT A RELEASE

Everything below is read off the PR branch. It can still change, or be rejected, before it lands — and the published experiment-98 build follows the branch, so what you install may be a few commits ahead of what you read here.

The branch also carries work that has nothing to do with firewall rules: folder mappings and the default memory/CPU limits move out of the gateway's database into ~/.huddle/config.json, host folders get indexed by huddle indexfolder so the portal can offer them in a folder picker, and there is a new folder-picker modal. Don't be surprised by it. This page is only about the rules.

Move your rules to a new environment

Only the shareable half of a rule travels. The row id, the request count, the last-seen time and the created/updated timestamps stay behind — they describe one install, not a policy. What is left is six fields, and those six are the whole contract between the two environments.

On the branch that contract shows up in four places at once: the API, the CLI, the portal, and a folder of JSON files your team keeps in version control.

WhatEndpointWhat it does
Export rules GET /api/rules/export Returns { version, exported_at, rules } with only the six shareable fields, ordered by domain. ?container=<name> or ?container=__global__ narrows the scope.
Import rules POST /api/rules/import Body { mode, rules }, with mode either merge or replace. Answers with { imported, updated, skipped }. ?container= remaps every incoming rule into that one scope.
Export a group GET /api/groups/:id/export The same rules, wrapped in a named envelope with a description and a shared flag.
Import a group POST /api/groups/import Creates the group, or updates the one that already carries that name, then upserts its rules.
Apply a group POST /api/groups/:id/apply Stamps the group's rules into one scope — global, or a single container.
Team folder, in POST /api/firewall-rules-folder/reload Re-reads every *.json in the mounted rules folder as a group.
Team folder, out POST /api/firewall-rules-folder/sync Writes the portal's groups back out as files, and prunes the ones that are gone.

The CLI is a thin client over exactly those endpoints, so anything you can do in the portal you can also script — and the other way round.

Two documents, one rule shape

There are two envelopes on this branch, and telling them apart is the single most useful thing to know. A flat rules export is a bag of rules with no name. A group envelope is the same rules with an identity: a name, a description and a shared flag. Both use the same six-field rule.

Flat rules — huddle firewall export
{
  "version": 1,
  "exported_at": 1717430400,
  "rules": [
    {
      "domain": "github.com",
      "container_id": null,
      "status": "allow",
      "path_pattern": null,
      "path_mode": 0,
      "expires_at": null
    }
  ]
}

No name, so nothing owns these rules. They land as loose rules in whichever scope you import them into.

A group — huddle firewall group export
{
  "version": 1,
  "kind": "huddle-firewall-group",
  "group": {
    "name": "OpenAI",
    "description": "Domains required for OpenAI …",
    "shared": true
  },
  "rules": [
    { "domain": "api.openai.com", "container_id": null,
      "status": "allow", "path_pattern": null,
      "path_mode": 0, "expires_at": null }
  ]
}

Named, so it stays a unit: it can be re-applied, re-exported or removed as one thing. A bare { "name": …, "rules": [ … ] } is accepted too.

The group envelope is the same format over the API and on disk in the team folder, so one file moves between installs, repos and teammates without translation.

The six fields

FieldMeaning
domainThe host. A leading *. wildcard is allowed, e.g. *.pkgs.dev.azure.com. Required, and matched case-insensitively everywhere.
statusallow or deny. The validator also accepts requested — the pending state from part 1.
path_patternOptional. * matches within one segment, a trailing * spans deeper segments — /dist/*. null means the whole host.
path_mode1 marks the host a path-allowlist: blocked at the root, only the listed paths pass. 0 for a normal rule.
container_idnull is global. Otherwise the devcontainer the rule belongs to.
expires_atOptional unix timestamp for a temporary rule; null is permanent.

Validation is fail-closed on both paths. An unknown field rejects the whole request with a 400, and every field is type-checked — so is an empty domain, and so is a status that is not one of the three. Nothing half-imports.

Doing it

Same operations, two front ends. Pick whichever suits the moment; a file written by one is readable by the other.

From the CLI

Export writes JSON to stdout, so it pipes. With --out it writes a file instead and the progress line goes to stderr, so a redirected run leaks nothing into your document.

$ huddle firewall export
$ huddle firewall export --container __global__ --out rules.json
$ huddle firewall export --container devcontainer-app --out app-rules.json

Import takes the file back, in the new environment:

$ huddle firewall import rules.json
$ huddle firewall import rules.json --replace
$ huddle firewall import rules.json --container devcontainer-app

Import prints its own summary — how many were added, updated and skipped. To see the rules themselves, list them by status. firewall list defaults to the pending ones, so ask for the allowed set explicitly:

$ huddle firewall list --status allow

Groups have their own four verbs. list prints id, name, rule count, whether the group is shared, and its source — manual for one you made yourself, startup-folder for one the team folder loaded.

$ huddle firewall group list
$ huddle firewall group export "NPM Registry" --out npm-registry.json
$ huddle firewall group import npm-registry.json
$ huddle firewall group import npm-registry.json --replace
$ huddle firewall group apply "NPM Registry"
$ huddle firewall group apply "NPM Registry" --container devcontainer-app

Group names are matched case-insensitively, and a name that matches nothing tells you to run huddle firewall group list. apply without --container means global. Creating, renaming and deleting a group are portal-only — the CLI has list, export, import and apply, nothing else.

In the portal

The Firewall page keeps the pending-request triage at the top. Underneath it is one panel, Firewall rules & groups — "every rule in scope, organised by group". The same panel appears on a container's detail page, scoped to that container plus global.

Down the left is a bucket list: All rules, then one entry per group, then Ungrouped, with a count each. Along the top right sit Import, Export, Sync to folder, Add rule and New group.

  • Export — with a group selected it downloads that group's envelope as huddle-group-<name>.json. Under All rules or Ungrouped it downloads the current view as a flat export, huddle-firewall-rules-all-<date>.json. So exporting is never blocked just because nothing is grouped.
  • Import — a file picker that takes both files the portal writes, and picks the endpoint from the document's shape: a group envelope restores the group and selects it, a flat export restores loose rules. Either way it merges.
  • Apply to — appears on the toolbar once a group is selected: a scope dropdown (Global, or a container) plus Apply, next to Rename / edit and Delete group. The note it leaves afterwards spells out what changed and where, including that the rules stay part of the group.
  • Tick some rows and a bulk bar appears — Export, Add to group, Path mode, Flip allow/deny, Delete, Clear — and its Export writes the same flat envelope for just those rows.

A group shows a Shared pill when it is meant to travel, and a From folder pill when the team folder loaded it. The table has Domain / path, Action, Container / Global and Group columns; a path-mode host shows a Specific paths (n) selector that expands into an Allowed paths editor instead of an Allowed/Denied pill.

Exports are self-contained: exporting a path-mode host pulls its allowed sub-paths in with it. Without that the host would import back blocked at the root, with nothing allowed.

Merge, replace, and the scope remap

This is the part most likely to bite someone. Import runs in one of two modes, and the scope you aim it at decides how much gets deleted.

ModeFlagWhat happens
merge default Upserts. An incoming rule that matches an existing one on (domain, container, path) has its status, expiry and path-mode updated; anything else is inserted. Nothing is ever deleted.
replace --replace Deletes the existing rules in exactly the scopes being imported, then inserts. Not the whole table — a document full of global rules leaves every container's rules alone.

The identity used for matching is deliberately loose in the right places: the domain is compared case-insensitively, and a missing path counts as an empty one. A rule stored as GitHub.com is the rule your document calls github.com.

Two duplicate entries inside one document are not an error. The first wins and the second counts as skipped — that is what the third number in the summary is for.

The scope remap: --container on import
rules.json
container_id: null
global rules
--container
devcontainer-app
One container
every rule rewritten to
container_id: "devcontainer-app"

Without --container, each rule keeps whatever scope the document gave it. With it, every rule is rewritten to that one scope — useful for taking a global ruleset and confining it to a single container, and a good way to surprise yourself if you forget the flag is there. __global__ is the name of the container-less scope, on both export and import.

One deliberate asymmetry worth knowing: --replace together with an explicit --container wipes that scope even when the document contains no rules at all. Importing an empty ruleset is how you clear a scope, and without this the delete would find nothing to do and replace would silently fail open.

TWO THINGS THE CODE DOES FOR YOU

Path rules get their marker. A path-scoped rule is inert over HTTPS unless its host is in path mode, so import establishes the host-level path_mode: 1 marker for every domain-and-container pair that received a path rule. Otherwise your imported path rules would be denied at CONNECT and nobody would know why.

Wrong door, right room. Hand a group envelope to huddle firewall import and it tells you it is a group and routes it to the group importer — unless you passed --container, which asks for a scope remap that only the flat importer can do, and then it imports the rules without the group. Hand a flat export to huddle firewall group import and you get an explicit error: this is a plain rules export, import it with huddle firewall import instead.

The team-managed rules folder

Files in a folder, one group per *.json, kept in Git. That is the whole idea: the folder is the source of truth for the groups it manages, and everyone pointed at it gets the same rules.

  1. 1
    Point Huddle at the folder. This only writes firewallRulesFolder into your CLI config — nothing is read yet.
  2. 2
    Restart the gateway so the folder is actually mounted. The gateway reads it at a fixed mount point the CLI binds; it never resolves your host path itself.
  3. 3
    The groups load on start, and whenever you reload.
$ huddle firewall folder set /path/to/firewall-rules
$ huddle restart
$ huddle firewall folder

huddle restart is new on this branch and it exists for exactly this: it recreates the gateway so a changed team folder gets mounted. folder set tells you to run it, and so does the portal when a sync fails on a folder that is still mounted read-only. huddle firewall folder on its own prints the configured path.

After that the folder moves in both directions, and the two commands are worth keeping straight:

$ huddle firewall folder reload

reload reads every *.json in the folder and reports how many groups, rules and errors it saw. It validates all the files before it touches live policy, and if any of them fails it changes nothing and keeps the last good policy — one malformed file cannot wipe your team's rules. Groups that vanished from the folder are dropped, so the folder really is the source of truth for what it manages.

sync goes the other way: it writes the portal's groups back out as files, prunes the stale ones, and reports how many were written and removed. The output is stable 2-space JSON with a trailing newline, so a synced folder stays Git-diff friendly. A file it cannot parse as a group envelope is left completely alone — never rewritten, never pruned. If the folder is still mounted read-only, sync says so and tells you to run huddle restart.

In the portal the same path is Settings → Team-managed defaults (extension & firewall rules) → Firewall rules folder, which has its own Reload button, plus the Sync to folder button on the Firewall page.

WHAT THE FOLDER DOES AND DOESN'T OWN

The folder only owns the rules it loaded itself. A group you made by hand is never overwritten from the folder — a reload refuses and reports it instead — and copies you applied to a container by hand survive a reload untouched. A group that disappears from the folder is deleted, and anything still pointing at it is ungrouped rather than orphaned.

Applying a group is what decides where it is in force. Its rules are stamped into the chosen scope and stay part of the group there, so it can still be exported, re-applied or removed as a unit. A rule that already exists in that scope is refreshed and adopted into the group.

Path mode: general URL vs dependency URL

The branch ships four ready-made groups in examples/firewall-rules/ — OpenAI, GitHub, Node.js and NPM Registry — and the rule of thumb behind them is the most portable thing on this page. Ask what kind of host you are allowing.

General URL → allow the whole host

An API or app you talk to, where the host is the service: api.openai.com. A plain allow, path_pattern: null, path_mode: 0. There is nothing to narrow down.

status: allow path_mode: 0
Dependency URL → path mode

A shared registry, download or source host where everybody fetches their own things by path: npm, PyPI, NuGet, Maven, a runtime's /dist/, GitHub repos. Block it at the root and allow only the paths you need.

status: deny path_mode: 1 + allow per path

The reason is worth saying out loud: on a whole-host allow, a compromised build can pull arbitrary code from that same host. Path mode is what stops registry.npmjs.org from becoming an open door because you needed one package from it.

{
  "version": 1,
  "kind": "huddle-firewall-group",
  "group": {
    "name": "NPM Registry",
    "description": "npm registry in path mode: blocked at the root, only the listed package/scope paths pass.",
    "shared": true
  },
  "rules": [
    { "domain": "registry.npmjs.org", "container_id": null, "status": "deny",  "path_pattern": null,            "path_mode": 1, "expires_at": null },
    { "domain": "registry.npmjs.org", "container_id": null, "status": "allow", "path_pattern": "/@types/*",     "path_mode": 0, "expires_at": null },
    { "domain": "registry.npmjs.org", "container_id": null, "status": "allow", "path_pattern": "/@angular/*",   "path_mode": 0, "expires_at": null },
    { "domain": "registry.npmjs.org", "container_id": null, "status": "allow", "path_pattern": "/typescript/*", "path_mode": 0, "expires_at": null }
  ]
}

The first rule is the marker: deny on the bare host, with path_mode: 1. Every rule after it is an exception. github.json does the same thing per org — /infosupport/* on github.com, /repos/infosupport/* on api.github.com — and nodejs.json allows only /dist/* and /download/* on nodejs.org. Swap the org and the package names for your own and you have your group.

One thing to watch

expires_at travels in the envelope. An allow rule whose timestamp is already in the past is not honoured by the gateway, and import does not warn you about it — so a ruleset exported with temporary approvals in it can arrive carrying dead rules that still look present in the list. Worth a finding if it catches you.
