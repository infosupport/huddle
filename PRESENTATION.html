De kernvraag

Hoe voorkomen we dat een container willekeurig internetverkeer doet — secrets lekt, malware downloadt, of meedoet aan een DDoS — zonder de developer experience te slopen?

Hoofdstuk 1 — Het Probleem

Risico's van ongereguleerde containers

Zonder DMZ heeft elke container effectief root-toegang tot internet én tot je Docker host. Dit zijn de zes meest reële risico's:

🔑
Lekkende Docker Credentials
Critical

Een gecompromitteerde dependency kan via de Docker socket containers spawnen die credentials exfiltreren naar een externe server.

🌐
Ongefilterd internet
Critical

Geen proxy = geen controle over welke domeinen een container bereikt. Een typo in een dependency lijst (typo-squatting) leidt direct naar malware.

🐍
Container breakout
Critical

Met een mounted Docker socket is een container effectief root op de host — een hele compromise pad is dan vrij.

🔍
Geen audit trail
High

Als er iets misgaat, weet niemand wat de container precies deed. Geen logging = geen verantwoording, geen forensics.

⚡
Resource exhaustion
High

Een runaway container kan 100% CPU of geheugen pakken en alle andere containers op de host blokkeren.

🔒
Geen lateraal beleid
Medium

Containers kunnen elkaar bereiken op het Docker netwerk en zo elkaar DDoS'en of binnenkomen.

Hoofdstuk 2 — De Oplossing

De oplossing: Huddle

Huddle is een DMZ Gateway die fungeert als de enige exit voor al het devcontainer verkeer. Eén plek waar je beleid afdwingt en alles logt.

💻
JetBrains IDE
host machine
🐳

🛡️

DMZ Gateway
🌍
Internet
untrusted

Alle HTTP/HTTPS verkeer moet door Huddle. Geen enkele container kan direct naar buiten.

Enforced

Eén beleidspunt

Eén plek waar regels leven — geen verspreide configuratie.

Auditable

Eén logstroom

Elk verzoek wordt vastgelegd met container-ID en tijd.

Huddle uit = container offline. Geen achterdeurtjes.

Hoofdstuk 2 — De Oplossing

Vier kernfuncties

Huddle bestaat uit vier onderdelen die samen het volledige verkeers- en toegangsbeleid afdwingen.

01
HTTP/HTTPS Proxy

Filtert verkeer per container en domain. Op een match met een allow-regel passeert het verzoek; bij deny krijgt de container 403.

poort 80
02
Docker Socket Proxy

Elke container krijgt zijn eigen UNIX-socket. Toegang is time-limited (1–120 min) en moet expliciet aangevraagd worden via de UI.

/tmp/dc-sockets/<id>.sock
03
Management API + UI

CRUD op firewall-regels, containerbeheer, snapshot-images. Web-UI om regels te reviewen en grants te verstrekken.

poort 3000
04
SQLite Database (WAL)

Persistente opslag van regels, grants en audit logs. Write-ahead log voor lage latency en tamper-resistente trail.

huddle.db
🎯 Kernprincipe: "deny all by default — allow only when explicitly approved."

Hoofdstuk 3 — Hoe het werkt

Docker Access Grants

Containers krijgen geen permanente Docker-toegang. Ze moeten expliciet om een grant vragen — een korte, tijdgebonden permissie die een mens goedkeurt.

1
Aanvraag

De container probeert /var/run/docker.sock te bereiken. De socket-proxy onderschept het verzoek en kijkt of er een actieve grant is.

2
Goedkeuring (mens-in-de-lus)

In de UI ziet de developer de aanvraag. Hij kiest een duur (1–120 minuten) en kent toe. Grant wordt opgeslagen in docker_grants met een until-timestamp.

3
Actief gebruik

Zolang until > now(), forward de proxy het verzoek naar de host Docker socket. Elk verzoek wordt gelogd.

4
Verloop

Na until is de grant automatisch verlopen — geen actie nodig. Een nieuwe aanvraag start de cyclus opnieuw.

💡 Waarom dit werkt: Iemand is altijd verantwoordelijk — geen anonieme "always-on" toegang, geen vergeten configuratie.

Hoofdstuk 3 — Hoe het werkt

jb-config.sh — het setup script

Bij elke containerstart draait dit script als root in de container. Het zorgt dat de container niet meer naar buiten kan zonder Huddle.

jb-config.sh — root@container
# 1. Locate JetBrains Remote Dev directory RDIR=$(find /jb-dist -maxdepth 2 -name "bin" | head -1) BUILD=$(cat $RDIR/../build.txt) # 2. Write host-config.json for JetBrains remote dev cat > ~/.config/JetBrains/host-config.json <<EOF { "build": "$BUILD", "workspace": "/workspace" } EOF # 3. Add audit header to ALL outgoing HTTP echo "proxy-header = X-Container-ID: $HUDDLE_CID" >> /etc/.curlrc # 4. Force ALL port 80 traffic through huddle:80 iptables -t nat -A OUTPUT -p tcp --dport 80 \ -j DNAT --to-destination $HUDDLE_IP:80 # Result: container CANNOT bypass the proxy. # Even if a tool ignores http_proxy env, the kernel reroutes it.

🔒 Defense layer 1: env var

http_proxy wordt door alle gangbare tools gerespecteerd (curl, wget, npm, pip).

🛡️ Defense layer 2: kernel

iptables DNAT vangt alles wat de env var negeert. Geen tool kan eronderuit.

Hoofdstuk 3 — Hoe het werkt

Architecture deep dive

Een gedetailleerd beeld van hoe een verzoek door het systeem reist.

🌊 HTTP-pad

Container → http_proxy of iptables DNAT → Huddle:80 → firewall check (container_id + domain) → allow/deny → internet.

🐳 Docker-pad

Container → mounted socket → socket-proxy → grant check (until) → forward naar host Docker socket of 403.

Hoofdstuk 4 — Eerlijkheid

Security Audit — bekende issues

We zijn transparant: Huddle is een proof-of-concept. Drie kritieke issues moeten dicht voor productie.

CRIT-01 Docker socket grant bypass

Container kan een vervalste X-Container-ID header injecteren en zo grants van andere containers gebruiken.

Critical

CRIT-02 Identity spoofing via client headers

Container-identificatie leunt op client-gecontroleerde headers en IP-cache. Beide zijn te beïnvloeden vanaf de container.

Critical

CRIT-03 Geen authenticatie op management API

Elke container op het netwerk kan via :3000 nieuwe containers starten, snapshots maken en Docker-grants uitdelen.

Critical
✅ Mitigaties:
  • Bind management API aan 127.0.0.1 of UNIX socket — niet meer bereikbaar vanaf containers.
  • Bearer token of mTLS op alle /api/* routes.
  • Verwijder NET_ADMIN capability — verplaats iptables-filtering naar de host bridge.

Hoofdstuk 5 — Vooruit kijken

Waarom Huddle nodig is

Vijf concrete redenen — elk is een scenario dat zonder Huddle gewoon gebeurt.

01
Containers kunnen secrets lekken naar externe services (GitHub, npm, telemetry endpoints) — vaak zonder dat iemand het merkt.
02
Containers kunnen DDoS-aanvallen uitvoeren of malware downloaden — jouw IP is dan de bron.
03
Zonder Huddle is er geen accountability — als er iets misgaat, wie wist wat en wanneer?
04
Containers kunnen de host compromitteren via misbruik van de Docker socket.
05
Zonder Huddle is er geen middenweg tussen full lockdown (productiviteit kapot) en open chaos (security kapot).

Bottom line: Huddle is de DMZ die je development environment beschermt tegen zelf-toegebrachte security-nightmares.
