# Host pipe

The gateway runs in a container and cannot see or run anything on the host. A few features need the
host anyway: browsing host folders (to pick mounts) and driving host-side environment tools such as
Docker Sandboxes (`sbx`). The **host pipe** is the one channel for that.

It is a folder, not a socket. Real FIFOs, Unix sockets and Windows named pipes do not cross a Docker
bind mount on every platform (a Linux container on Windows cannot reach a named pipe, and `bind()` on
a Windows drive mounted into WSL fails), but plain files do. Python-free, stdlib-only Node on the host.

```
host                                   gateway container
~/.huddle/pipe/   <── bind mount ──>   /huddle-home/pipe/       (existing ~/.huddle mount, no new one)
```

Devcontainers and sandboxes never get this folder mounted. Only the gateway (which already holds the
Docker socket, i.e. is already fully trusted by the host) and the host agent can write to it.

The agent trusts every request file, so that is enforced: `huddle init` passes the host path of
`~/.huddle` to the gateway (`HUDDLE_HOST_HOME_DIR`), and every devcontainer workspace, folder mapping and
sandbox workspace is refused when it is `~/.huddle` or inside it, and only allowed read-only when it
contains it (the home folder, a drive root). Compared case-insensitively; symlinks are not resolved. This
also keeps `config.json` (with the operator token) out of containers. The one exception is
`~/.huddle/sbx/links/<name>/rw|ro`, which the host agent builds for a sandbox's folder mappings (below): it
holds only links to the mapped folders, and the gateway mounts nothing else from there.

## Lifecycle

- `huddle init` (and `huddle restart`) starts the host agent in the background, replacing a running one
  so it always runs the current CLI version: `huddle pipe serve`, detached, `windowsHide`, logging to
  `~/.huddle/pipe/host.log`.
- `huddle pipe status` / `huddle pipe stop` / `huddle pipe serve` (foreground, for debugging).
- The agent writes a heartbeat `~/.huddle/pipe/host.json` every 2 s:
  `{ "v": 1, "pid": 123, "version": "<cli version>", "platform": "win32|darwin|linux", "tools": ["sbx"], "startedAt": "<iso>", "updatedAt": "<iso>" }`
  The gateway treats the agent as **offline** when the file is missing or `updatedAt` is older than 10 s.
- On start the agent deletes leftover `*.in`, `*.busy`, `*.out`, `*.tmp` older than 1 hour.
- The pipe folder is the user's alone. `huddle init` and the agent create it `0700`, and the agent refuses to
  serve from a symlink, from a folder another user owns, or from below a parent others can write to (its own
  parent is closed to group and others). Files are written `0600`. Requests carry no further authentication:
  whoever can write there is the user or root, and can run `sbx` directly anyway. On Windows the folder
  inherits the profile's ACL.

## Protocol (v1)

All files are UTF-8 JSON, written to `<name>.tmp` and then renamed (atomic), so a reader never sees a
half-written file. `<id>` is a random 32-hex string generated by the caller.

1. Gateway writes `<id>.in`:  `{ "v": 1, "op": "<op>", "args": { ... } }`
2. Agent polls every 100 ms, claims a request by renaming `<id>.in` → `<id>.busy` (so it is handled once
   and slow requests run concurrently), runs it, writes `<id>.out`, deletes `<id>.busy`.
3. Gateway polls for `<id>.out`, reads and deletes it.
   Reply: `{ "ok": true, "result": ... }` or `{ "ok": false, "error": { "code": "<code>", "message": "..." } }`
4. Timeouts (gateway side): if `<id>.in` is still unclaimed after 5 s the gateway deletes it and fails with
   `host_pipe_offline` (it fails right away when the heartbeat is missing or stale). Once claimed, it waits up
   to the per-op timeout (default 30 s; for `tool.run` the `timeoutMs` it passes plus 10 s, so the agent's own
   timeout reply wins) and then fails with `host_pipe_timeout`.

Error codes: `bad_request`, `unknown_op`, `not_found`, `not_allowed`, `tool_missing`, `internal`
(agent side); `host_pipe_offline`, `host_pipe_timeout` (gateway side).

### Operations

| op | args | result |
|---|---|---|
| `host.info` | `{}` | `{ platform, version, home, tools: { [name]: { available, path?, version? } } }` |
| `fs.list` | `{ path?: string }` | `HostFolderListing` (below). No `path` → the roots. |
| `tool.run` | `{ tool: string, args: string[], timeoutMs?: number }` | `{ code: number, stdout: string, stderr: string }` |
| `sbx.links` | `{ name: string, links: { id, hostPath, readOnly }[] }` | `{ rw: string \| null, ro: string \| null, skipped: { id, reason }[] }` |
| `sbx.kit` | `{ caPem: string }` | `{ dir: string }` |
| `ssh.key` | `{}` | `{ publicKey: string }` |
| `ssh.host` | `{ alias, port, user, hostKey }` or `{ alias, remove: true }` | `{ publicKey: string \| null }` |

**`fs.list`**: lists the immediate subfolders of one folder (port of `host-browse.ts` from
`feat/sbx-sandboxes-rebased`). No path → roots: every readable drive `X:/` on Windows, `/` elsewhere, plus
the home folder. Paths are host paths in Huddle notation (forward slashes, upper-case drive letter, no
trailing slash except roots: `C:/Users/me`, `/home/me`). Hidden folders and symlinked folders are included;
at most 2000 entries, then `truncated: true`. A folder that cannot be read → `ok:false`, `not_found`.
Sorted case-insensitively.

```ts
interface HostFolder { path: string; name: string }          // name: leaf, or 'C:' / '/' for roots
interface HostFolderListing { path: string; folders: HostFolder[]; truncated: boolean; max: number }  // path '' for roots
```

This is **not** an authorization boundary. Mount paths are still validated by `hostPathError` and the
operator token, exactly as before; listing only replaces the old `huddle indexfolder` snapshot.

**`tool.run`**: runs an allowlisted host binary with an argv array, never a shell. The allowlist lives in
the host agent (`TOOLS` in `cli/src/pipe/tools.ts`), today only `sbx` (override the binary with
`HUDDLE_SBX_BIN`). The binary is resolved on `PATH` (`sbx`, `sbx.exe`); `.bat`/`.cmd` are refused (cmd.exe
would let argv inject commands). stdin is closed, `windowsHide: true`, output capped at 16 MB per stream.
Interactive commands (TTY) are not supported. A tool that runs past `timeoutMs` (max 15 min) is killed and
the reply is `ok: true` with `code: 124` and a `[huddle] timed out` line in stderr; a signal gives `128 + n`.
Only allowlisted tools that are actually installed are listed in the heartbeat's `tools`.

**`sbx.links`**: (re)builds `~/.huddle/sbx/links/<name>/` for one sandbox: one link per folder mapping in
`rw/` or `ro/` (a junction on Windows, which needs no admin rights; a symlink elsewhere), each folder 0700.
The old folder is removed first without following any link in it; an empty `links` only removes it. A
mapping that does not exist, is not a folder, resolves into `~/.huddle`, or contains `~/.huddle` while
writable is left out and listed in `skipped`. `rw`/`ro` are the host paths of the folders that got links.

**`sbx.kit`**: writes `~/.huddle/sbx/kits/huddle-ca/`, an sbx v2 mixin kit that makes a sandbox trust the
Huddle CA (see "TLS inspection" under sbx egress), and returns its host path. `caPem` must be one PEM
certificate; the files are rewritten on every call, with LF line endings.

**`ssh.key`** / **`ssh.host`**: SSH into a devcontainer (Connect IDE) without setting up a key, like `sbx setup ssh`
does for sandboxes. `ssh.key` makes Huddle's own ed25519 key pair in `~/.huddle/ssh/id_ed25519` once (on the host,
private key 0600; the gateway only gets the public key, which it puts in the container's authorized_keys) and puts
`Include ~/.huddle/ssh/hosts/*.conf` at the top of `~/.ssh/config`. `ssh.host` writes `~/.huddle/ssh/hosts/<alias>.conf`
(`Host <name>.huddle` → `127.0.0.1:<relay port>`, user, that key, `IdentitiesOnly`) and pins the container's host key
in `<alias>.known_hosts` (`StrictHostKeyChecking yes`); `remove` deletes both. Alias, port, user and host key are
validated so nothing can be injected into the ssh config. The portal link is a JetBrains Toolbox link to the alias,
and `ssh <name>.huddle` works from a terminal too.

## Gateway side

- `gateway/src/host-pipe.ts`: `hostPipe.call(op, args, { timeoutMs })`, `hostPipe.status()`
  (reads the heartbeat). Pipe dir = `${HUDDLE_HOME_DIR}/pipe` (override `HUDDLE_PIPE_DIR`).
- `gateway/src/environments/`: provider registry, so sbx is one implementation, not a special case.

```ts
interface EnvironmentProvider {
  id: string;                 // 'sbx'
  label: string;              // 'Docker Sandbox'
  status(): Promise<ProviderStatus>;                         // { id, label, available, version?, error?, agents: string[] }
  list(): Promise<SandboxInfo[]>;                            // { name, provider, status?, workspaces?: string[] }
  create(spec: SandboxSpec): Promise<SandboxCreateResult>;   // spec: { name?, agent, workspaces: {path, readOnly}[] }
  remove(name: string, opts: { force: boolean }): Promise<void>;
}
```

Adding an environment = one provider file in `gateway/src/environments/` + its binary in the host
agent's `TOOLS`. Nothing in the API, the pipe or the frontend is sbx-specific.

Huddle only removes sandboxes it created: a provider-agnostic table `sandboxes(provider, name, created_at)`.
Providers reuse names, so every successful list drops the records of sandboxes that are gone (only records
older than that list, so a create finishing meanwhile is kept); a new sandbox with an old name is not Huddle's.

### HTTP API (operator token, like every other `/api` route)

| method + path | body / query | response |
|---|---|---|
| `GET /api/host-pipe` | | `{ online, version?, platform?, tools?: string[], updatedAt? }` |
| `GET /api/host-folders` | `?path=` | `HostFolderListing`; 503 `{ error: 'host_pipe_offline' }`, 404 `not_found`, 400 invalid path |
| `GET /api/environments` | | `{ providers: ProviderStatus[] }` |
| `GET /api/environments/:provider/sandboxes` | | `{ sandboxes: (SandboxInfo & { managed: boolean })[] }`; `managed` = created by Huddle |
| `POST /api/environments/:provider/sandboxes` | `{ name?, agent, workspaces: {path, readOnly}[] }` | `SandboxCreateResult` `{ name, ok, steps: {label, command, code, stdout, stderr}[] }` |
| `DELETE /api/environments/:provider/sandboxes/:name` | `?force=1` | `{ ok: true }`; 404 if Huddle did not create it |
| `PUT /api/environments/:provider` | `{ enabled: boolean }` | `{ enabled, steps }`; switching on also starts a recreate of every sandbox |
| `POST /api/environments/:provider/recreate` | | `RecreateState` `{ running, reason, startedAt, finishedAt?, results: {name, ok, message?}[] }` |

A provider that is switched off answers list, create and remove with 409 `{ error: 'provider_disabled' }`.
`ProviderStatus` carries `enabled`, `unavailableReason?` (why it cannot be switched on) and `recreate?`.

Removed: `GET/POST/DELETE /api/indexed-folders`, the `indexed_folders` table (dropped on startup), and the
`huddle indexfolder` CLI command.

### sbx (first provider)

argv only, via `tool.run` with tool `sbx`:

- status: `sbx version`
- list: `sbx ls --json` (fall back to parsing the `sbx ls` table)
- create: `sbx create [--kit <huddle-ca kit>] --name <name> <agent> <path> [<path>[:ro] ...]` (first workspace is
  never read-only), timeout 15 min
- remove: `sbx rm [--force] <name>`, then `sbx.links` with no links
- folder mappings: see below

Sandbox names: `^[a-z0-9][a-z0-9-]{0,62}$`; default `huddle-<leaf of first workspace>-<4 hex>`.
Agents offered: `claude`, `codex`, `copilot`, `gemini`, `shell` (provider-defined list).

Out of scope for now: policy reconcile.

### sbx egress

While sbx is switched on in Huddle, every sandbox reaches the network only through the Huddle firewall,
under a rule scope of its own: `sbx:<name>`.

- **Listener.** The gateway runs a second proxy listener on port 3128. `huddle init` publishes it on host
  loopback only (`127.0.0.1:${HUDDLE_SBX_PROXY_PORT:-32768}`) and passes the port as
  `HUDDLE_SBX_PROXY_HOST_PORT`; without it the provider cannot be switched on.
- **Identity.** sbx has one global upstream proxy setting, `proxy.sandbox`, but a sandbox keeps the value
  it was created with, and the sbx daemon sends its credential as `Proxy-Authorization` on every request
  and CONNECT. The sandbox never sees it. So every create runs, one at a time:
  1. `sbx settings set proxy.sandbox http://<name>:<secret>@127.0.0.1:<port>` with a fresh 256-bit secret
  2. `sbx create ...`
  3. `sbx settings set proxy.sandbox http://_huddle-reset:<reset secret>@127.0.0.1:<port>`, also when the
     create failed

  The gateway stores only the SHA-256 of the secret (`sandboxes.proxy_secret_hash`) and the spec
  (`sandboxes.spec_json`), and only when all three steps worked. Secrets are masked (`:***@`) in every
  step shown to the portal.
- **Unknown callers.** No credential, an unknown secret, a secret under another sandbox's name, or sbx
  switched off: all get 407.
- **Reset secret.** It belongs to no sandbox. sbx rebuilds every sandbox's proxy from the global setting
  when its daemon restarts, so a sandbox that presents the reset secret means Huddle no longer knows which
  sandbox is which. The request is denied, and every sandbox is recreated with a new secret. This happens
  at most once per 5 minutes, and never while a recreate is already running.
- **Recreate all.** Runs in the background:
  - It starts by forgetting every old secret.
  - Each sandbox listed by `sbx ls --json`, including ones Huddle did not create, is removed with
    `rm --force` and created again from its stored spec, or else from the agent and workspaces in the
    listing.
  - Anything inside a sandbox outside its workspaces is lost; the workspaces are host folders and stay.
  - A sandbox that cannot be recreated is stopped, so it does not keep setting off the reset secret.
- **Switching on:**
  - Saves the user's own `proxy.sandbox`, unless it already points at Huddle. The database keeps it
    with its password masked; the full value lives in gateway memory only. After a gateway restart a
    password cannot be put back, so switching off unsets the setting and the step says to set it again.
  - Sets the reset URL.
  - Restarts the sbx daemon. From then on every existing sandbox is denied until it has been recreated.
  - Only now is sbx marked on, and everything is recreated. If the restart fails, the user's own setting
    is put back, sbx stays off, and the error is returned.
- **Switching off:**
  - Restores the saved `proxy.sandbox`, or unsets it.
  - Restarts the daemon, so running sandboxes drop Huddle.
  - Only when both worked: marked off, and every secret forgotten. A failure leaves sbx on, so it can be
    tried again. A recreate that is still running leaves the sandboxes it has not reached yet alone.
- **Gateway restart.** Once the host pipe answers, the gateway first reads `proxy.sandbox`. If sbx is on but
  the setting no longer points at Huddle, the gateway stopped in the middle of a switch-off: it restarts the
  daemon and marks sbx off. If sbx is off but the user's setting is still saved, it stopped in the middle of a
  switch-on: it puts the user's setting back (when it still points at Huddle), restarts the daemon and stays
  off. Otherwise it lists the sandboxes. If any has no known
  secret (the gateway stopped in the middle of a create), it recreates them all. Until the pipe answers,
  it tries again every 30 s.
- **One firewall: Huddle's.** sbx's own network policy would ask a second time for what Huddle already
  allowed. So every sandbox Huddle creates gets `sbx policy allow network --sandbox <name> "**"`: before the
  create when sbx takes it, else right after (a failure shows in the steps; the sandbox then still asks). The
  rule goes before `sbx rm`, and for every sandbox on switch-off, when sbx's policy is the only firewall again;
  a rule that cannot be removed keeps Huddle on (switch off again to retry).
  Deny rules (yours or an organization's) still win, and under organization governance local allows do nothing.
- **Folder mappings.** Settings → Folder mappings with a host folder go into every sandbox too (Docker
  volumes stay devcontainer-only). Before the create, `sbx.links` links them into
  `~/.huddle/sbx/links/<name>/rw` and `/ro`; those go to `sbx create` as two extra workspaces, `ro` with
  `:ro`. After the create, `sbx exec <name> -- sh -c <script>` links each one to its container path, with
  `/home/vscode` read as the sandbox user's `$HOME`. What the sandbox had at that path is moved to
  `<path>.huddle-orig`. A mapping that cannot go in is listed in the create's steps and does not fail it.
  Checked against sbx v0.39.0 on Windows (`sbx-folder-links-poc.mjs`): the file share follows the links on
  the host side, `:ro` holds through them, and links the sandbox makes in `rw` never reach the host. The
  stored spec keeps only the real workspaces; a recreate links the current mappings again.
- **Connect an IDE.** The sandbox detail page asks `GET /api/environments/sbx/sandboxes/<name>/ide-link?ide=vscode|jetbrains`.
  The first time per gateway run that runs `sbx setup ssh` on the host, which makes every sandbox reachable as
  `<name>.sbx` from the host's ssh config. The link (VS Code Remote-SSH, or the JetBrains Toolbox App's `jetbrains://gateway/ssh/environment`) points at that alias and
  opens the first workspace folder when it is a POSIX path. SSH is inbound and does not go through the Huddle proxy.
- **TLS inspection**, as close to a devcontainer as sbx allows. Every create gets `--kit` with the kit
  `sbx.kit` wrote: as root at create it puts the Huddle CA (and sbx's own proxy CA, from
  `PROXY_CA_CERT_B64`) in the system store with `update-ca-certificates`; `NODE_EXTRA_CA_CERTS`,
  `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` point at that system bundle (not at the Huddle CA alone, which
  would break sbx's credential proxy); and on every start a background watcher imports the CA into the
  keystore of each JetBrains backend under `~/.cache/JetBrains/RemoteDev/dist`. A sandbox created that way
  is stored with `huddleCa`, and only for those the sbx listener terminates TLS; for others (an older host
  agent or an sbx without kits, which then gets a create without `--kit`) CONNECT stays a raw tunnel, decided
  on the host alone, where path-mode domains are denied. The `huddle` host stays closed to sandboxes either way.
  This holds for the paths where sbx passes TLS through to Huddle (`forward-bypass`, `transparent` in
  `sbx policy log`). For hosts sbx injects credentials into (`forward`), sbx's daemon on the host terminates
  TLS itself and makes the upstream TLS through Huddle, and it does not trust the Huddle CA: switch TLS
  inspection off for such a domain in the firewall (below).
- **TLS inspection off, per domain.** A host-only rule can have `no_intercept` (Firewall → a rule's menu, or
  `POST /api/rules/:id/no-intercept { enabled }`): the proxy then keeps a raw tunnel for that domain, for
  devcontainers and sandboxes alike, wherever the rule applies (its container, sandbox, or globally; a
  `*.` rule covers its subdomains). It is kept in rule and group exports (only when on, so older Huddles
  still import the file). Path mode needs inspection, so the two exclude each other; putting a domain
  in path mode switches inspection back on.
